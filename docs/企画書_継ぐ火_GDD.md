## 2. コンセプト

**一文：「文明とは、忘れる前に書き残せた分だけ速く積み上がる」**

知識は人の記憶に宿る一時資産であり、石版化すれば盤石に、書き残さないままだと「回り道・停滞」のコストを払う世界。テックツリーを1段ずつ解錠して文明を積み上げる高揚感（発注者の好み）を中核に据える。

### 2.1 ターゲットと難度分離（アシスト自壊への回答）

| 層 | 遊び方 | アシスト |
|---|---|---|
| コア層 | 手動配置最適化＋探索編成の詰め | 使わない |
| ライト層 | 最適化を省略 | アシスト機能で代替 |

アシストは**設計上の約束として「理論最大効率の80%止まり（準最適）」に固定**する。

- 推奨配置ワンタップ ＝ 貪欲法で局所最適の8割
- おまかせ成文化 ＝ 残存tick降順の単純ヒューリスティックで8割
- 探索編成テンプレ ＝ 平均戦力充足の8割

手動最適化には常に **+20%相当の上澄み**（隣接シナジー3連接・過密回避・trait適材配置の複合）を残す。この「80/100約束」を `balance.json` の設計不変条件として明文化し、**全代表盤面で `アシスト出力効率 ≤ 手動理論最大 × 0.85` をassert**する。

**[2026-07-31裁定] 推奨配置の「80/100約束」の実装定義（M26 実装の正本化。実測で素の貪欲が理論最大の 98.3% に達したため、「貪欲だから8割」は成立しない）**:

- **採点尺度 = 盤上全施設の産出乗数の総和**（`boardOutputScore`）。基礎産出で重み付けしない（施設ごとに産出資源が異なり加算に意味がないため）。
- **準最適化は明示パラメータ**: 各手で最大増分 maxΔ を求め、目標 = maxΔ × qualityRatio（**engine 定数 0.65**・content 化しない=裁定N2と同型。運営 LLM の additive 追加でアシスト強度を動かせてはならない）。qualityRatio=1.0 で素の貪欲へ厳密退化。
- **中立手の床**: 目標が「空きセルへ置く中立手（Δ=1.0）」を下回らない。わざと過密ペナルティを踏む提案を禁止（代償として盤面比の下限は約 0.71）。
- **手の順序（どの施設から置くか）はアシスト対象外**。並べ替え・後戻りなし。+20% の上澄みは主にここに残る。
- **「80%」の測り方 = 盤面全体の乗数総和の比**（既存施設も分母分子に含む）。代表盤面の要件: ①アシストが置く施設が過半 ②**最適配置が中立配置より 25% 以上良い**こと（相性の悪いタグ構成では中立ですら 0.85 を超え、上限 assert が構造的に満たせない盤面が実在するため検証対象から除く）。
- qualityRatio 0.65 は縮約 content（施設4種）での校正値。施設14種投入後の再校正は M39〜M41。

**[2026-07-31裁定] おまかせ成文化・探索編成テンプレの「80/100約束」の実装定義（M27 実装の正本化・上記 M26 裁定と同型）**:

- **成文化の理論最大 = 「間に合う記録の件数を最大化する理想の順番」**（成文化キュー1本前提の総当たり最適）。GDD 既定の「残存tick降順」ヒューリスティックは理論最適の向き（残存tick昇順＝EDD）の真逆であり、**それ自体が自然に8割弱（実測平均 0.770）となるため調整パラメータなしで約束を満たす**（M27 テストで実証・固定済み）。
- **成文化は「一度に1件ずつ」前提で計算**（研究と同一の単一キュー構造＝M6/M13 の設計に整合）。将来「複数人での並行記録」を導入する場合は本アシストの再調整が必須（申し送り）。
- **成文化の候補は「実地で使った住民が現存する tech」のみ**。研究完了でも保持者ゼロ（未使用）の tech は候補に載せない（失われる記憶自体がまだ無いため。§4 のコアループとの整合）。
- **探索編成の理論最大 = 現在派遣可能なメンバーで組める最強編成の総合戦力**。qualityRatio は **engine 定数 0.75**（M26 の 0.65 と同じく content 化しない）。実測平均 0.796。ratio=1.0 で最強編成へ厳密退化（総和不変証明つき）。
- **編成の床 = 候補プール平均相当のランダム編成**。それを下回る提案は禁止（M26 の中立手の床と同じ発想。わざと弱い編成を組まない）。
- 0.75 / 実測 0.770・0.796 は縮約 content での校正値。M39〜M41 の再校正対象。

### 2.2 放置系との構造衝突への回答

赤バッジ（即損失）の常態化を数値で抑制する。

- 日常危機化する「想起困難」は**緩衝（生産一時停止・回復可能）であって喪失ではない**。
- **赤バッジ**は (B)レア資産が実際に喪失へ近づく特定状況（唯一保持者を派遣中 × 士気危機の重なり等）にのみ限定点灯。
- 通常の想起困難は**黄バッジ（先延ばしコスト）**に留める。
- 「見なくても大損しない」基準線 ＝ **72h放置でクリティカルパス(A)は一切失われない**（sim保証項目）。
- 喪失恐怖はアシストで減らせないため、ライト層は難度シード**「穏」（想起困難頻度0.5倍・(B)出現頻度低）**を選べる。ターゲットミスマッチを難度選択で吸収する。

**[2026-08-01裁定・台帳v9 必-4] 難度シード「穏」の機械可読定義（M53 実装の正本化）。** 「想起困難頻度0.5倍」＝想起リスクの**全加算項**（`basePFix` / `moraleBonusMidFix` / `moraleBonusLowFix` / `dispatchWFix`）と上限 `pMaxFix` を ×0.5。「(B)出現頻度低」＝探索の負傷蓄積（`injuryPerFailureFix`）を ×0.5（死亡→唯一保持者喪失が (B) 喪失の主経路であるため、最も副作用の小さい実現）。`lossClass` 自体の書き換えは大移動の継承点獲得式（§10.3）に波及するため不採用。実装は content への純粋な値写像で RNG 不使用（`src/difficulty.ts`）。数値の妥当性は M39〜M41 で再校正。難度選択 UI とセーブへの永続化（`difficultySeedId`）は未実装であり、現状は既定「標準」固定（台帳v9 追-5）。

### 2.3 セッション想定

1回5〜15分、1日1〜3回。初回のみプロローグ移動（実プレイ2〜3日）で周回カタルシスを1週間以内に体感させ本編（初回2〜4週）へ。

**開始5分の体感（MVP必須要件、三段構成）：**
1. 配置1回で緑オーバーレイ → 生産数値が **+15%** 上がる成功体験（配置パズルの魅力）
2. その住民の技術で小クラフト完成（価値の実感）
3. 直後にその一時住民が離脱し、未成文の知識が数分で目前で消える（喪失）

「喪失デモ一点張り」を廃し、**価値を実感させてから失わせる**構成を必須化する。

## 3. 世界観

**「長夜明け」**：超巨大噴火（または衝突体）由来の成層圏エアロゾル**『幕塵（まくじん）』**が陽を翳らせ、世界が長夜に沈んだ火山冬／核の冬モチーフ。実在気候現象ベースでファンタジー物質に非依存。

文字を書ける者が絶え、知識は「知っている人がいる間だけ在る」口伝文化に。プレイヤーは共同体**『隷（えい）』**の差配役**『継ぎ手』**を務める。

### 3.1 Dr.STONE回避の核心

- 石化・全人類同時停止・全知全能個人を使わない。
- 復活の起点を**個人の知識独占ではなく集団の断片記憶の再統合**に置く。
- テーマ軸を「天才の科学万能譚」→「忘却に抗って書き残す文明継承」へずらす。
- トーンは荒涼から再生への暖色（**ダークテーマUI不使用**＝CLAUDE.md準拠）。

幕塵は各地で不均一に晴れ、光の戻った**『澄み地』**は資源が再生し、翳り地は枯れる。この不可避の資源移動が周回（大移動）の物語的必然となる。

## 4. コアループ

3層ループ。各層に実損リスクと質的選択を持たせる。3層は「**分＝書き残す／日＝誰に握らせ誰を守るか／週＝何を遺し誰を連れるか**」で貫かれる。

### 4.1 分単位＝手入れ層（約5分）

(a) 緊急度バッジ順にタスク確認（赤＝B喪失接近／黄＝想起困難など先延ばしコスト／灰＝任意）。
(b) 成文化キュー：誰がどの未成文技術を握るか＋想起リスク%表示。
(c) 住民配置微調整。
(d) クラフト／研究キュー投入。
(e) 探索編成・派遣。

全タスクはホームハブから各画面へワンタップ遷移。

### 4.2 日単位＝経営層

オフラインtick差分を復帰時に離散事象で解決。

**日常フック「想起困難」：** 未成文技術の保持者を過酷業務（製錬／鍛冶等の高負荷施設）・探索派遣・士気切れに晒すと、その技術に一時的想起困難が確率発生し、当該住民の関連生産が一時停止（喪失でなく回復可能な緩衝）。技術は **解禁 → 実地稼働で記憶定着 → 成文化で盤石** の二段構え。発生確率・持続・回復は `recallRiskFormula` として数式化（§10参照）。

**セッション終端の合図（罪悪感駆動是正）：** 手入れ完了時に「**今日のタスク完了。次の危機は最短でも約X時間後**」の完了バナーを表示（必須）。Xは決定論計算＝次の想起困難最短予定・保管庫充填予定・探索帰還予定の最小値。

**[2026-07-31裁定] X の定義の縮約（M29 正本化・台帳v5 必-2）。** 想起困難は粗粒度ベルヌーイ抽選（§11.2）であり「次の発生予定 tick」が存在しないため、X は**確定予定のある事象のみの最小値**＝「探索帰還予定・保管庫充填予定・成文化完了予定」に縮約する（engine 変更なし・表示の意味を正直にする）。危機予定表を持つ改修は観測可能挙動の変更（golden 再生成+bump）を伴うため採らない。バッジ 0 件時は §2.2 の基準線文言（72h 放置でも (A) は失われない）を表示する。

**オフライン復帰UX：**
- 復帰専用**「帰還ダイジェスト画面」**を情報アーキテクチャに独立追加（11→12画面）。復帰時に必ず最初に表示。**ネガティブ先頭単独表示 → ダイジェスト → ドリルダウン**の3段。**[2026-07-31裁定・台帳v5 追-3]** 「必ず」の適用条件＝**セーブからの復帰かつ経過 60 tick（ゲーム内1時間相当）以上**のときのみ表示（数分の再訪で毎回挟む煩わしさの回避。判定は catch-up 適用前の目標 tick で行い、長期不在ほど出ない逆転を防ぐ）。
- 複数喪失トリガー同時発生への対応：「保留は1回」を撤回。**復帰後の緊急成文化フェーズ（実時間制限なし・プレイヤーが確定操作するまで）中に発生予定だった全喪失トリガーをまとめて保留し、優先順につき1手ずつ緊急成文化を許す**。2件目以降の即時確定を排除し「何もできず重要資産喪失」の抜け穴を塞ぐ。

### 4.3 週単位＝戦略層

探索網拡大 → 衛星拠点自動供給 → 本拠格子拡張 → エラ壁テック到達 → 次時代解禁。幕塵後退／枯渇メーターが進み大移動判断へ。移動前最終週＝**何を石版に選び誰を連れて行くか**のヤマ場。

## 5. テックツリー

時代区分5段（MVPはE1〜E3）。各エラ末尾に壁テック1つ。`researchCost` は entity 個別値（`tech.researchCost` 固定値）駆動。グローバル数式は目安レンジ（min/max）のスキーマ上限下限チェックにのみ使用。

### 5.1 コスト設計（指数コスト vs 線形供給 / era間インフレの是正）

旧「30×1.35^累計解禁数」を廃止し二重是正：

**(1) エラ内リセット式**
`エラ内コスト = base_era × 1.2^(当該エラ内クリティカルパス解禁済み数 n)`

- **n の定義：** クリティカルパス（壁テック＋その前提）のみをカウント。週次追加の横展開葉テックは **n に一切算入しない**。
- **n の上限＝各エラのクリティカルパス本数で固定**（E1=3 / E2=3 / E3=4 程度）。
- 「n がエラ別上限を超えないこと」を累積回帰テストのlintで機械強制。葉テックを何本足しても単一era内で `1.2^n` が爆発しない。

**(2) 逓増率を共に ×2 へ統一**（旧 x3/x2 不一致の解消）

| エラ | base_era | 研究点供給 era_multiplier |
|---|---|---|
| E1 | 30 | 1 |
| E2 | 60 | 2 |
| E3 | 120 | 4 |
| E4 | 240 | 8 |
| E5 | 480 | 16 |

コスト側・供給側とも階段比 ×2 で揃え、era移行直後のコスト/供給比スパイクをゼロにする。階段状の高揚感は「大きくなる数字そのもの＋intra-eraの 1.2^n ＋新レシピ/施設の解禁＋印刷での成文化 -50%」という**内生加速**で担保し、時間停滞を伴わずに体感を出す。era移行後 N tick 窓の実効研究速度低下を専用sim項目で監視。

**(3) 壁テック到達時間管理はクリティカルパスのみカウント。**横展開葉テックは到達レンジに影響させない。

### 5.2 時代骨格と代表テック（初回標準シード目安）

## 6. コロニーと配置

### 6.1 格子

- 初期 **6×8 = 48セル**。初期利用可は一部、残りは瓦礫セル（開墾で解放）。
- 1セル＝1施設（大型は 2×1 / 2×2 占有）。
- 施設14種：かまど / 貯水槽 / 菜園 / 寝床 / 作業台 / 炭焼き窯 / 製錬炉 / 鍛冶場 / 研究机 / 写字室 / 保管庫 / 見張り台 / 探索本部 / 療養所（各 Lv1〜5）。

**[2026-07-30裁定] footprint の実装形（M16 正本化）。** footprint は 1×1 / 2×1 / **1×2** / 2×2 の矩形を許可（縦長 1×2 は本節の「2×1」の向き違いとして同格。schema の footprint レンジ 1〜2 と整合）。state は「アンカーセル＋footprint」で持ち占有セル集合は導出、セーブでは 1×1 をキー省略する正準形（saveSchemaVersion v1→v2、旧ビルドが新セーブの大型施設を黙って 1×1 に潰さないための版差）。隣接判定は **state の footprint を権威**とする（content 側を権威にすると既存盤面の占有形状が content 変更で遡って変わる。content 側の `facility.footprint` が読まれるのは **`placeFacility` の焼き込み時のみ**で、隣接判定では読まれない。M17 実装済み）。

### 6.2 隣接行列（実装単位）

`adjacency.json` は**タグ×タグ対称行列**。施設は `facility.tags[]` を保持し、実装はタグペアで解決（施設ペア非依存）。新施設追加の記述量は O(タグ種数²) 固定＝タグ7種で49セル以下、施設をいくら増やしても行列不変。

**タグ7種：** 熱源 / 清浄 / 汚染 / 騒音 / 湿潤 / 静穏 / 学芸

**隣接ルール（8近傍静的判定・パスファインディング不使用）：**

| ルール | 効果 |
|---|---|
| 熱源 × 熱源 | 鍛冶加工 +20% |
| 汚染 × 寝床・療養所 | 健康 -15%/tick |
| 学芸 3連接 | 成文化 +30% |
| 湿潤 × 菜園 | 食料 +15% |
| 湿潤 × 熱源 | 効率 -10% |
| 見張り台 | 外周ほど防衛係数上昇 |

### 6.3 判定規則の確定事項

- **大型施設の判定基準セル：** 全占有セルの外周8近傍の和集合から自セル群を除外し重複除去した集合を基準とする。ボーナスは占有面積に依らず**1施設1回のみ計上**（占有セルごとに多重計上しない）。`adjacency.json` スキーマとUIプレビュー両方の共通ロジックとして実装前に確定。
- **複数タグ施設の過密判定：** タグ単位で独立集計。1施設が複数タグを持つ場合、各タグの過密カウントに**同時参加**する（熱源かつ騒音の施設は両タグに別々にカウント）。
- **過密ペナルティの順序基準：** 「同一タグ施設が8近傍に3つ以上密集で3つ目以降ボーナス無効化＋超過1施設につき当該タグ効率 -10%」の「3つ目」判定は、対象セルを**方向順（N, NE, E, SE, S, SW, W, NW 固定）で列挙後、安定文字列（セルID）辞書順に再ソートする**。**[2026-07-27裁定・旧文言「先頭2件のみ通常ボーナス、3件目以降を無効化＋ペナ」を改訂(裁定N10)]** 有効件数は **(threshold-1) 件**（既定 threshold=3 ゆえ 2 件）であり、超過分は無効化＋ペナ。**どの個体が有効になるかは現行の効果モデル（6.2 のタグ×タグ行列）では結果に影響しない**——ボーナス項は (自施設のタグ, 近傍のタグ) のペアのみで決まり近傍の個体に依存しないため、辞書順選抜は挙動として観測不能である。**それでも決定論のため常にセルID辞書順で選ぶ**（将来ボーナスが施設ペア依存へ拡張された瞬間に順序非決定が静かに混入するのを防ぐ保険。engine 側は現状維持）。全ボーナスは加算 → 単一係数 **±60%上限クランプ**、過密ペナはクランプ外で別途減算適用。
- **[2026-07-30裁定] 大型施設×判定の細目（M17 正本化）。** ①「1施設1回のみ計上」は**近傍側の大型施設にも適用**する（2×1 の近傍が基準セル2個に接しても1回。判定は施設単位の重複除去。根拠＝本節の「超過1**施設**につき」）。②過密ペナ減算後の下限クランプは**タグ横断の合計に対して1回**（タグごとではない。T5 以来の挙動で sc16 の golden が固定済み）。③(c) の辞書順選抜における大型施設の代表セルID＝**アンカーセル番号**（どのセルで接しても基準はアンカー。N10 の「観測不能だが常に辞書順」は維持）。
- **[2026-07-27裁定] ±60%クランプは engine 定数（裁定N2）。** 上記の単一係数クランプ ±60% は **engine 側の定数のままとし、content 化しない**。この値の変更は決定論バンドルの観測挙動を変える＝golden vector が変化するため `algoVersion` bump を要する（ADR-016）。content 側から調整可能にすると運営 LLM の additive 追加が algoVersion に波及しうるので、CODEOWNERS 人間専用領域である engine に留める。

### 6.4 単調解回避

1. 過密ペナは MVP 必須実装。
2. 難度シードに「**資源露頭配置・初期利用可セル形状・一部タグ係数の ±20% シード揺らぎ**」（`adjacency.json` のシード依存オフセット、レンジ制約内）を導入。タグ行列の骨格は不変だが係数と地形が周回で変わり、最適レイアウトが状況依存に切り替わる。

## 7. 住民

### 7.1 ステータスと生産式

ステータス（0〜100・上限厳守）：**体力 / 器用 / 知性 / 頑健 / 意志**。基準50。

`生産量 = Σ(担当者関連ステータス寄与) × 施設Lv係数 × (1 + Σ隣接補正) × trait倍率`

**[2026-07-27裁定] ステータス英字IDの正本(裁定B8)。** `event.nodes[].statWeights` のキー等、JSON content で参照する際は以下の英字IDを正本とする。

| 日本語名 | 英字ID(正本) |
|---|---|
| 体力 | `vigor` |
| 器用 | `dexterity` |
| 知性 | `intellect` |
| 頑健 | `fortitude` |
| 意志 | `will` |

8.2 の判定式に現れる「**戦力**」は上記5種の基礎ステータスではなく**派生値**であり、英字IDは `combatPower` とする（算出式は engine 実装時に確定・8.2 参照）。基礎ステと同じ名前空間で扱わないこと。

### 7.2 特性（trait, MVP 8種）

学者 / 職人 / 探索者 / 記憶巧者（生きた書庫） / 病弱 / 楽観 / 悲観 / 怪力。負特性込みで凹凸。

- `trait.effects[]` は各係数に min/max（ステータス倍率 ±30%以内、成文化速度倍率 0.7〜1.5 等）。
- 同種効果は乗算合成 → カテゴリ別上限クランプ。
- **[2026-07-28追補・M5実装の正本化(ユーザー承認済み)]** ①**合成後クランプの確定値**（1効果あたりの min/max は上記のまま、trait 3個を合成した後の総倍率に対する engine 定数）: ステータス倍率は合成後 **[0.7, 1.3]**、生産 trait 倍率は合成後 **[0.7, 1.5]**。②**`trait.effects[].stat` の名前空間**: 5正本ID（`vigor` 等）を指す効果は**ステータスへの効果**として 7.1 の「ステータス寄与」項に入り、予約語 **`yieldMul`** を指す効果は 7.1 生産式の「× trait倍率」項に直接乗る。効果はどちらか片方のみを通り**二重計上しない**。③生産式へ写せない未実装効果（`health`/`researchSpeed` 等）はロード時に reject せず「**記録して読み飛ばし**」（`unrepresentedTraitEffects` に機械可読で保持し、該当システム実装時に移す）。未知語彙は reject（隣接効果と同じ）。
- **1住民の trait 保持上限 ＝ 3個に固定**（スキーマ強制）。組合せ爆発を有限化。敵対botに「最強trait3個持ちを重要ポジション（唯一保持技術）へ集中配置するbot」を追加してカバー。

### 7.3 愛着メカニクス（fatal「愛着が存在しない」への正面回答＝MVP実装）

乱数ロスの言い換えに堕さぬよう、住民ごとの情緒接続を3機構でMVP実装する。

1. **決定論エピソードログ（memoirLog）：** seed＋プレイ履歴から決定論生成される簡易バイオ（出自・口癖・恐れ）と、イベント駆動で追記される記録（「初めて『製錬』を成文化した」「近郊探索で△を保護した」「□と鍛冶場で共に37日働いた」等）。テンプレ＋確定値で生成、LLM実行時生成は不使用。件数上限で古いものは要約に畳む。
2. **絆（bond）：** 同一施設で共働した住民ペアに bond 値が決定論蓄積し、士気補正＋と士気回復＋を生む。相方の喪失で bond 相手に一時的士気ペナ（喪失の重みを残る住民の数値挙動で表現）。
3. **記憶の可視化：** 住民カードに「この人にしかない記憶」＝保持する (B)rareIrreversible テック/銘設計図/習熟ボーナス（該当施設効率 +最大25%）をアイコン＋一文で常時明示。喪失時は「〇〇は『製錬の勘所』と、△を保護した日の記憶を長夜に還した」と、失った内容を具体名で提示。

これにより (B) 喪失は数値損失でなく「この人が覚えていた/一緒にやった何か」の喪失として接続する（手触りはプレイテスト依存、残余リスク参照）。

**[2026-07-30裁定] 定数の正本化（M12 実装値の追認）。** 簡易バイオのテンプレは **8 種**（出自・口癖・恐れの組合せ骨格）、memoirLog の件数上限は **12 件**（超過は古いものから要約に畳む）。bond は **上限 100**・共働 1 日あたり **+1.0** の決定論蓄積、**節目 10 / 25 / 50** で memoirLog へエピソード追記（節目の記録 tick は区間終端でなく**解析的な到達 tick**、1 区間で複数節目を跨いだ場合は**超えた節目を全段記録** — いずれも分割不変性の要請。M13 裁定）。相方の喪失時は **bond 値の 50% を一時士気ペナルティ**として bond 相手に与える。いずれも暫定定数であり、バランス調整段（M39〜M41）で再評価する。tick 結線（蓄積・節目判定の実行タイミング）は M13 で recall 結線と同時に行う。

### 7.4 技術喪失の二層（fatal「フックがsim要件と矛盾」への回答）

| クラス | 定義 | 喪失可否 |
|---|---|---|
| **(A) criticalRecoverable** | クリティカルパス技術 | 失っても必ず再取得可能（ソフトロック防止の保証範囲、喪失＝停滞コストのみで詰まない） |
| **(B) rareIrreversible** | 希少特性・銘設計図・習熟ボーナス・探索一点物・特定住民の複合記憶 | 一回性喪失を許容 |

「取り返しのつかない喪失」は (B) のみ、(A) には使わない。境界は `tech.lossClass` で機械区別し、sim検証も (A) のみ再取得保証・(B) は保証対象外と明示。

**[2026-07-30裁定] 一回性喪失の state 表現（M13 正本化）。** 死亡処理（§11.7 段70）で「生存保持者ゼロ かつ 記録ゼロ」となった tech は `ResearchState.loss{tick, irreversible, lastHolderId}` に記録され、completedTick は null・progress は 0 に戻る。(A) は再研究可能、(B) は研究対象から外れる（周回内喪失＝§10.2 と同一規則）。段70 内の処理順序は **death memoir → partnerLost（bond 士気ペナ）→ 技術喪失** の固定順（memoirLog のバイト列を決める仕様）。

**[2026-08-01裁定・台帳v8 追-1] 成文化の担い手（M50 正本化）。** 成文化を進めるのは**研究点を産出する施設（作業台等）で稼働している就労者**（MVP に「学者」職は存在しないため研究係が兼ねる解釈・進行レートは当該施設の稼働就労者数）。研究と成文化が人手を取り合わない（機会費用が乗らない）側面は認識済みで、専用の成文化スロットを設けるかは M39〜M41 のバランス調整で様子を見てから判断する。

### 7.5 住民寿命モデル（sim(4)成立への回答）

住民に決定論寿命 `lifespanTick` を付与：seed駆動の**離散対数正規近似**（平均＝約300日相当＝**432,000tick**、σ＝平均の **0.25**）からサンプル。記憶巧者は `memoryDecayDelay = 1.5`（成文化猶予＝寿命換算で1.5倍の余裕）。`残存想定tick = lifespanTick − ageTick` を機械算出し、設計時ルールと sim(4) の「唯一保持者残存想定tick ≥ 成文化所要tick × 安全係数」に供給。パラメータは balance/townJSON に格納。

**[2026-07-29裁定] 離散化の実装形（M11 正本化）。** 対数正規はオーサリング時に**等確率64分位の倍率表**（`townParams.lifespanQuantileMul`）へ展開して JSON に格納し、実行時は「uint32 draw → 整数除算で添字 → 表引き → 平均寿命に乗算」のみ（§11.7 の「非整数べき乗はオーサリング時展開」を分布に適用）。σ を書き換えて表を直さない静かな分布変更はローダーが整数演算の整合検査で reject する。また**死亡は entity 削除ではなく tombstone**（`life.diedTick`）とし、死者は生産・想起判定から除外されるがデータは残る（7.3 の memoirLog/bond が死者を参照するため。セーブ肥大は周回リセットで抑制）。

**[2026-07-31裁定] 成文化アシストの猶予算出（M27 正本化）。** 「あと何tickで失われるか」は、その tech の生存保持者のうち**残存想定tickが最小の住民**の値を使う（`残存想定tick = lifespanTick − ageTick` ＝本節の機械算出をそのまま流用。専用の余命計算は持たない）。

### 7.6 人口下限保証（経済空洞化への回答）

人口が `min(寝床上限 × 0.5, 6)` を下回ると漂着加入頻度 ×1.5、かつ**最低6人を絶対保証**（6未満なら次回加入イベントを前倒し確定）。sim検証に「全tick・全敵対botで人口 ≥ 下限」の不等式を追加。

**[2026-08-02裁定・台帳v12 必-2] 下限保証の適用範囲。** 本節の絶対保証は**周回内の死亡経路**に適用される（担い手=死亡ゲート・下記）。**大移動の乗員選抜は対象外**であり、新周回の開始人口=乗員数（6人未満もあり得る。プレイテスト Round 1 で3周連続大移動により人口6→1を実測）。少人数開始からの回復は本節の漂着加速（頻度×1.5）が担い、乗員が少なすぎる大移動への警告/最少人数ガードの数値は M39 の「大移動の実行ガード再評価」（台帳v9 必-2）に束ねて確定する。

**[2026-07-29裁定] 絶対保証の担い手は死亡ゲート（M11 正本化）。** 加入の前倒しだけでは加入が寝床上限に縛られるため「全 tick で下限以上」は保証できない。よって人口を減らす唯一の経路（死亡）に**「生存人口 − 1 < 下限なら死亡させず次の加入 tick へ延期する」ゲート**を置き、これを絶対保証の担い手とする（加入頻度 ×1.5 は回復の加速）。同一 tick では加入（段65）→死亡（段70）の順で前倒し救済が成立する。下限の整数化は **ceil**（人口は整数のため `≥ 寝床×0.5` と同値。floor では本節の不等式より弱くなる）。暫定定数（**バランス調整段 M39〜M41 で要再評価**）: 加入間隔 `arrivalIntervalTicks = 4320`（3日）、加入時年齢 60〜240日（`joinAgeMinTicks`/`joinAgeMaxTicks`）、加入住民の初期士気 50。

### 7.7 獲得と規模

初期数名 / 寝床上限内の決定論的定期加入（晴天漂着）/ 探索での保護 / 衛星拠点次世代（長期）。常時 **8〜20人規模**。人物・寿命は seed 決定論生成。割り振りは施設ごと就労スロット（Lvで増加）、適性外配置も可だが効率低下。

腕利き鍛冶職人＝鍛冶テックの生き字引が同時に探索即戦力、というように技術は実地で扱った住民の記憶に紐づく。プレイヤーは能力でなく「その人が何を覚えているか」で人を惜しむ。

### 8.2 決定論解決

派遣確定時に `seed = hash(worldSeed, "exploration", dispatchTick, teamIds, destId)` を固定。目的地JSONのイベントテーブルから seed 列で決定論的にイベント列（3〜8ノード）生成。

`成否 = (関連チーム総合力 + 装備補正 + seededRoll(0..R)) ≥ difficulty`

関連ステータスはイベント種別で変わる（踏破＝体力/頑健、遭遇＝戦力、遺構解読＝知性、罠＝器用）。

**[2026-07-27裁定] 「戦力」は基礎ステータスではなく派生値(裁定B8)。** 7.1 の5種（`vigor`/`dexterity`/`intellect`/`fortitude`/`will`）と異なり、「戦力」はそれらと装備から算出される**派生値**であり、英字IDは `combatPower` とする。**算出式は engine 実装時に確定**する（本裁定はID正本の確定のみで、式は未確定）。`statWeights` に `combatPower` を書く場合、ローダーは基礎ステと別扱いで解決する。

**[2026-07-29裁定] combatPower の算出式確定（M7 実装の正本化）。**

`combatPower(住民) = clamp(0, (Σ_s w_s × 実効ステータス_s + Σ派生add) × clamp(Π派生mul, 0.7, 1.3), 100)`

- **重み配分**: `vigor` 0.35 / `fortitude` 0.30 / `dexterity` 0.20 / `will` 0.15 / `intellect` 0.00（総和ちょうど 1.0 ＝ 基礎ステと同じ 0〜100 スケール。中立住民＝全ステ50 の戦力はちょうど 50）。知力を 0 とするのは、知力は研究・成文化系で活きる設計であり戦闘にまで効かせると万能ステータス化するため。
- **重みは engine 定数**（`src/engine/rules/stats.ts` の `COMBAT_POWER_WEIGHTS`）。content/balance に**切り出さない**（裁定 N2＝隣接クランプ±60% と同じ判断）。変更はコード変更＝golden vector 差分＝algoVersion bump の正規の関門を必ず通る。バランス調整需要が生じたら「balance へ移設＋総和 1.0 のローダー強制追加＋bump 1回」で移行可能。
- **装備は combatPower に含めない**。本節判定式が「関連チーム総合力 **+ 装備補正**」と装備を別項で加算するため、combatPower 側に混ぜると二重計上になる。分解は `装備込み最終戦力 = combatPower + 装備補正`（装備補正の実装は探索エンジン側）。
- **trait は 2 段で効く**（基礎ステへの効果 → 重み付き和 → 派生値への直接効果 `stat: "combatPower"`。各経路 1 度だけで二重計上なし）。`yieldMul` は生産量専用の係数であり combatPower には**効かない**。

**イベント列の確定タイミング：** 派遣確定時点でイベント列（判定結果・分岐・確定数値・報酬）を丸ごとセーブにスナップショット書込み。以後テーブルを一切再参照せず再生。週次でテーブルにadditive追加されても未帰還セーブの結果は不変。

### 8.3 判定前の質的分岐（一本道収束への回答）

一部ノードにプレイヤーの質的分岐を実装：

- 各判定ノードに直前選択「**撤退＝資源半分確保で以降ノード打ち切り安全帰還 / 強行＝全取得を狙うが失敗時の負傷リスク ×1.5**」。
- 分岐種として「**慎重（成功率＋/報酬−）**」「**大胆（報酬＋/難度＋）**」の二択をイベント定義で選べる。

stat合計最大化一本道から「判定前の意思決定」へ変える。分岐は `event.nodes[].choices[]` としてスキーマ化。文面分岐（名前/装備種別/負傷有無）は既視感対策として維持するが、意思決定の質は choices が担う。

### 8.4 帰還報酬とログ

報酬：資源、設計図（未知テック前提1つを埋める/実地要件を一部肩代わり）、衛星拠点候補座標、稀少品（(B)レア資産）。

**帰還ログのスナップショット形式：** 確定時に `logTemplate` ＋パラメータから**レンダリング済みの完成文字列そのもの**をセーブに保存し、以後テンプレを再参照しない（後日のテンプレ修正・tombstone化で過去ログが壊れない）。ログ保持上限 **50件**、超過分は要約統計に畳む。

### 8.5 全滅リスクと安全曲線

総合力が難度を大きく下回り続けると負傷累積 → 撤退不能 → 一部脱落 → 最悪全滅。全滅は (A) なら再研究で回復可・(B) は永久喪失。クリティカルパス唯一保持者全損でも (A) 再取得ルートが残ることを balance の静的グラフ解析で保証。難度は装備で管理可＝無謀を咎めるが理不尽全滅はしない曲線。

### 8.6 探索ROIにB喪失リスクを金銭化（核心フック空洞化への回答）

`探索ROI = 期待報酬 / (逸失生産 + 期待B喪失損失)`
`期待B喪失損失 = Σ(全滅確率 × 派遣者が保持する(B)資産価値換算)`

これにより「唯一/レア保持者を派遣に出すか本拠で書き残させるか」が経済的に発火。ROIは距離帯ごと **1.2〜2.0** のレンジ（新人のみ派遣時）に収め、(B)保持者派遣は損失項で不利化する。sim検証に「貪欲botが唯一/レア保持者を派遣する頻度」の観測を追加。

**[2026-08-07裁定・M39 ⑯で明確化] 1.2〜2.0 は「距離帯ごと」＝帯に出せる event の平均に掛かる制約であり、帯内の**個別目的地**には掛からない。** 目的地選択が意味を持つには帯の中に差が要る（R9-A01「近郊3目的地の期待報酬 125.5/125.7/125.7薪・投資効率3件とも 1.28 で判別不能」）ため、M39 ⑯ で帯内を「取り分の厚み × 必要人数」の梯子に分化した。結果として **3名編成では ROI 1.2 を割る目的地が帯ごとに1本ある**（近郊=瓦礫原 1.02 / 遠隔=風車小屋 1.12）——これは「その目的地は4名で行け」という意図的な設計であり、帯平均は 3名/4名の両方で 1.2〜2.0 に収まる（実測: 4名 1.265/1.365/1.420、3名 1.229/1.333/1.419）。§8.1⑤ の「校正点は新人3〜4名」も帯平均に対する校正点として読む。

### 8.7 MVPイベント本数

距離帯あたり深部厚め（近郊3 / 遠隔3 / 深部4 ＝ 計10本、平均5ノード＝約50ノード）。残りは週次JSON追加。item（装備）にも min/max レンジ制約を課し、装備1個で全探索バランスを崩す穴を封じる。

### 9.2 衛星拠点＝前哨基地

探索確保地点に住民1〜4名常駐 → 特定資源を決定論tickで本拠在庫へ自動供給。タイプ別供給（鉱山＝鉄/石炭、農園＝穀物、林＝薪/繊維、湧水＝水、遺構＝研究点/稀少品）。

**維持コスト・供給・逓減（数式明示）：**

- `供給 supply = baseSupply(type) × 常駐人数 × 拠点Lv × (1 − 翳り率)`
- `維持 upkeep = 食料baseFood × 常駐人数 + 士気ケアbaseMorale × 距離帯係数`
- `翳り率 = clamp(0, 幕塵後退度 × 拠点固有shadeSensitivity, 1)`。翳り率 **0.7超**で供給 < 維持 → 放棄推奨をUI明示。
- `ネット収益 = supply資源換算 − upkeep` を拠点カードに常時数値表示。維持 > 供給の死重が生じない baseSupply 初期値を sim（拠点網ROI）で担保。

襲撃は戦力値判定（拠点防備＋常駐戦力＋seededRoll vs 襲撃強度）。放棄/移設可。全て静的tick計算（常駐AI経路探索なし）。

**[2026-07-31裁定] M24 実装の正本化（本節の空白 3 点の確定）**:

- **MVP の拠点タイプは 鉱山(iron)/農園(grain)/林(firewood) の3種**。湧水は水資源が MVP 資源系に無く、遺構は研究点産出で `outpostType` スキーマ（§12.1・resource 産出のみ）に構造的に載らないため MVP 外（入れる場合はスキーマ拡張を伴う別裁定）。
- **hazard{intensity, growth} の意味論 = 「駐在員が (B) 資産を失う期待確率」**（探索の全滅リスク §8.2 の拠点版）。プレイヤーは探索と拠点で同じ感覚の数字を読む。
- **capacityCurve は facility の `outputPerTickByLevel` と同型の配列**に baseSupply × 拠点Lv を折り込む（オーサリング規律・6桁floor・検証器を施設と共用）。
- **拠点網 ROI の式（§11.4-7 の検証対象）** = `supply ÷ (upkeep + 期待B喪失損失)`。期待B喪失損失 = hazard 強度 × Σ(B資産価値換算)。資産価値換算は探索 ROI（§8.6）の `rareAssetValueFix` を再利用し、**同一資産への二重値付けを禁止**。ネット収益（上記の差の式）と ROI は両方を算出・表示する。
- 距離帯維持費係数（near 1.0 / far 1.4 / deep 1.8）は**暫定値**であり、§8.1⑦ の既裁定（balance.exploration は全て暫定・M39〜M41 で再評価）に含める。
- **[2026-08-01裁定・台帳v8 追-2] 拠点の設置コストは MVP ではゼロ**（本節が維持費と供給しか規定しておらず、engine が値を発明すると content 側で調整できなくなるため）。導入する場合は `outpostType` スキーマへの content 項目追加として行う（M39〜M41 の再評価対象に登録済み）。
- **[2026-08-05裁定・台帳v18 必-1] 拠点供給は本拠の加算式保管上限＋廃材スポンジを通る**（M64 の上限会計統一。従来は上限を無視して本拠在庫へ直加算＝Round 4 で穀物 76,980 まで実測された乱れの根）。連続流用の `applyCappedIntake` で毎 tick クランプされ、超過分は廃材変換される。上限会計は本拠生産/拠点供給/探索報酬の3系統とも §6.7 の加算式（基礎400＋保管庫Lv加算）に統一（探索報酬のみ生産会計非経由＝§8.1⑥ 改訂参照）。

## 10. 長期・周回

### 10.1 長期目標と勝利条件

E5『通信塔』完成＝他隷との交信成功＝**初回本編クリア**。以後は多隷ネットワーク構想（周回累積解禁の遠大目標, v1.1+）。

### 10.2 プレステージ＝『大移動（Exodus）』

幕塵後退/枯渇メーター臨界または任意発動。

**B資産を大移動に集約（major「クライマックスとB資産が別イベント」への回答）＝2プール競合：**

1. **石版プール：** 成文化済み(A)技術＋「石版化可能な(B)」（銘設計図・成文化した習熟ノート）を、キャラバン容量（石版換算枠）で奪い合わせる。積めなかったものは長夜に還る＝(A)は次周再取得可・(B)は永久喪失。
2. **乗員プール：** 「生きた記憶としての(B)習熟」を握る住民本人を、乗員定員 `crewCap = ceil(生存人数 × 0.5) + 継承ボーナス` の枠で選抜。連れて行けば習熟保持、置き去れば当該住民と(B)習熟を永久喪失。

**[2026-08-02裁定・台帳v12 必-2] 新周回の開始人口 = 乗員数。** §7.6 の人口下限保証（死亡ゲート）は乗員選抜に適用されない（6人未満の新周回開始もあり得る）。回復は §7.6 の漂着加速が担う。最少乗員の警告/ガード数値は M39 の実行ガード再評価（台帳v9 必-2）で確定。

**[2026-08-01裁定] 超過時の挙動（M28 正本化・台帳v7 追-3）。** 実行コマンド（`executeExodus`）は容量超過が1件でもあれば機械可読 reject（`exodusCapacityExceeded`）で**拒否**する。「超えたら何が落ちるか」を返す resolver（`resolveExodusPlan`）は UI プレビュー専用。黙って大事な資産が落ちる事故を構造的に防ぐ。また大移動後の**新周回の開始状態（初期施設配置等）の生成は M53「ニューゲーム生成」が担当**（初回起動と同じ生成器を通す・台帳v7 必-2）。**[2026-08-01裁定・台帳v9 追-6]** 同じ並びで、**乗員 0 人の大移動も機械可読 reject（`exodusNoCrew`）で拒否**する（新周回が住民 0 人で始まり進行不能になるため。M53 で追加・既存セーブ/golden/algoVersion への影響なしを確認済み）。

これで大移動が「石版を多く積むか、腕利きを多く連れるか、どのBを諦めるか」の情緒的クライマックスに一致。探索死亡の受動的B喪失も残すが、能動選択の主戦場は大移動に移す。

**キャラバン容量式：**
`容量 = ceil(想定石版総数(到達エラ) × 0.35) + 継承点ボーナス`

「想定石版総数(到達エラ)」は各エラのクリティカルパス＋標準想定葉テック本数からなる**静的テーブル値**とし、週次葉テック追加では変動させない（セーブ互換単純化）。実プレイの石版総数が増えても持ち出し比率が30〜40%レンジを外れないよう、テーブル値を運営の統計クリープ検出対象に含め、逸脱時は次バージョンのマイグレーションでのみ更新（周回内は固定）。

**[2026-07-27追補] 媒体別重み。** 石版プールの「石版換算枠」は記録の**媒体別重み**（石板 1.0・紙 0.25、§11.1 追補）で消費される。容量式は不変。周回中は「紙＝安いが焼失しうる／石板＝高いが不滅」、大移動では「紙＝軽い／石板＝重い」と有利が反転するため、移動前最終週に「石板をそのまま積むか、学者時間を使って紙へ写本し直して枠を稼ぐか」の選択が加わる（§4 のヤマ場を強化する意図）。

### 10.3 継承点（meta進行）

- 獲得：`継承点 = round(到達エラ × 10 + 成文化率(%) × 0.5 + 生存住民数 × 2)`
- 購入コスト：`cost(n) = 50 × 1.5^(購入済み段階n)`、各ボーナスに上限段階。

**代表周回対比表（標準シード）：**

| 周回 | 内訳 | 獲得点 | 到達段階 |
|---|---|---|---|
| 1周目 | 到達E3(30) + 成文化率60%(30) + 生存12人(24) | ≒84点 | 1段目(50)を1周で購入可 |
| 2周目 | 合算 | — | 2段目(75)到達 |
| 3周目 | 合算 | — | 3段目(113)到達 |

各ボーナス上限 **4段（50/75/113/169、累計407点）**で概ね4〜5周で1系統上限。全3系統フル解放に12〜15周。1〜3周で必ず意味ある選択ができ、上限まで無力感なく進む範囲に段階数を調整。sim検証(6)に「代表周回で1周あたり最低1段階購入可能かつ全系統上限到達に10〜18周のレンジ」の数値不等式を追加。

**[2026-08-07裁定・台帳v21 必-4 / M39 ⑭で最終化] 1段目コストは 45 点（式の 50 ではない）。** 上の `cost(n) = 50 × 1.5^n` は 2段目以降（75 / 113 / 169）の正本として存続するが、**1段目だけ 45 点に下げてある**（`balance.exodus.inheritTierCosts = [45, 75, 113, 169]`・累計 402 点）。理由は上の代表周回表が想定する「到達E3 + 成文化率60% + 生存12人 = 84点」が**初回周回には楽観的すぎた**ことで、実プレイの初回周回は Round 8 で 49 点 / Round 9 で 72 点（おまかせ編成）であり、50 点だと 49 点の周回が「中核ループが1項目も買えない空振り」になる（R8-06）。M39 が夜間ゲート実 run（40ゲーム日・15run）の獲得点 56〜98 と併せて実測確定した。1段目だけを下げるのは「入口を下げても上限までの総額（402 点）と全系統上限到達 15 周（GDD 11.4-6 のレンジ [10,18] 内）を動かさない」ためである。

**[2026-08-01裁定] 獲得式3語の機械可読定義（M28 正本化・台帳v7 追-1）。** ①**到達エラ** = 完了済み研究の tech が属するエラの order の最大値（壁テック越え基準は MVP に E4 が無く代表周回表と食い違うため不採用）。②**成文化率の分母 = 研究完了した tech の本数**（content 全 tech 本数を分母にすると週次の葉テック追加で過去周回の継承点評価が動き、§10.2 が容量式で明示的に避けた content 依存が再発するため）。③**継承3系統 = キャラバン容量 / 乗員定員 / 開始備蓄**（`startingStock`＝次周の初期在庫ボーナス。研究速度・幕塵後退は tick ループに触れ golden を動かすため3つめに採らない）。数値（`balance.exodus`）は全て暫定で M39〜M41 再評価。10〜18周レンジの実証は M36〜M38 の sim 担当。

### 10.4 上限後の死蔵回避

余剰継承点で「**高難度シード解放**」（幕塵後退が速い/初期資源少/敵対強度高）と「**実績図鑑一部**」を解放でき死蔵しない出口を MVP 確保。

### 10.5 周回シード生成の決定論

`新worldSeed = hash(前worldSeed, 周回回数, 累計継承点)` の純粋関数導出（`Date.now`/`Math.random` 不使用）。UIで任意シード文字列入力も併設。周回時 RNG カウンタを全ドメイン0リセット。

**[2026-08-01裁定] リセット対象は RNG カウンタと worldSeed のみ（M28 正本化・台帳v7 追-2）。** ゲーム内時計（tick）は周回をまたいで**連続**とする（0 に戻すと `bornTick`・memoir・`completedTick` 等の全時刻の付け替え（rebase）が必要になり、直列化も負 tick を受け付けないため。本節がリセットを求めているのは乱数状態だけ、という読みを正とする）。

### 10.6 周回を質的に変える

1. 高難度シードで幕塵後退速度・初期条件・adjacency係数 ±20% 揺らぎ・地形を変え毎周異なる最適解を要求。
2. 大移動発生条件を周回で厳格化。
3. 周回目標（全成文化/最速登攀/(B)コンプ）を提示。

恒久ボーナスは上限クランプで青天井暴走を防ぎつつ意思決定を別種へ置換。

### 10.7 完結構造

(1) 勝利条件（通信塔）明確、(2) 周回＝自己ベスト最適化で無限成立、(3) 全テック完全成文化目標、(4) シード共有で擬似競争。新JSON追加は寿命延長であって存在前提でない。

### 11.1 経済数式

`yield = baseYield × facilityLv係数 × (1 + Σ隣接補正) × (Σ担当者ステータス寄与 / 50) × trait倍率`

- 1tick = 1分、オフライン差分 72h（**4320tick**）クランプ。
- 施設増築 `cost(Lv) = base × 1.15^(Lv−1)`。
- 開墾 `base × 1.15^解放数 + cap`。
- 研究コスト＝entity個別値、逓増はエラ内クリティカルパス数リセット式、供給 era_multiplier ×2 でコスト側 ×2 と追随（era間比一定）。
- 成文化：記録1枚＝**媒体別コスト**（石板＝粘土 × 時代係数・紙＝紙 × 時代係数）＋学者作業時間 × 媒体別倍率。E3印刷のコスト -50%・速度 ×2 は**紙媒体のみ**に適用。媒体の仕様は下記 [2026-07-27追補] を正とする。
- 記憶劣化：常時劣化なし、喪失トリガは ①死/全滅 ②寿命（記憶巧者遅延） ③大移動置き去り ④**可燃記録の焼失**（イベント駆動のみ・下記追補。焼けるのは「記録」であって知識そのものではない）。士気低下・過酷業務・派遣時のみ一時想起困難（回復可）。
- 戦闘：`勝敗 = (Σ防衛戦力 × 配置ボーナス + seededRoll) vs 襲撃強度(時代逓増)`、全滅回避フェイルセーフ有。
  - **[2026-08-06追認・台帳v21]** M66 実装の解釈をユーザー追認で確定: ①「外周ほど防衛係数上昇」(6.2)は外周セルか否かの**2段**(連続勾配は発明しない。大型施設は代表セル=アンカーで判定・6.3③と同規約) ②「時代逓増」は到達エラ(`reachedEraOrder`)を再利用(engine が2つめのエラ定義を持たない) ③**全滅回避フェイルセーフ=襲撃で住民は死なず施設も壊れない**。損害は在庫の一部略奪のみ(略奪は消費の単一経路を通り生産会計には算入しない)。あわせて 11.7 段10(予約だった襲撃判定段)は M66 で実装済み。

**[2026-07-27追補] 記録媒体システム（石板/紙）— 最小構成で確定。**

成文化の産物「記録」に媒体を導入する。媒体は **engine 既知の2種固定（enum）**とし、新 content カテゴリは作らない。

| 媒体 | コスト/学者時間 | キャラバン重み(石版換算枠) | 可燃 | 備考 |
|---|---|---|---|---|
| 石板 `stoneTablet` | 高・遅（基準 ×1.0） | 1.0 | 不燃 | 粘土コストの廃材代替（§6.7 の3出口）は石板のみに適用 |
| 紙 `paper` | 安・速 | 0.25 | 可燃 | E3印刷の -50%・×2 は紙のみに適用 |

- 数値パラメータ（`costMul`/`timeMul`/`caravanWeight`/`flammable`）は balance 系 JSON の `recordMedia` ブロックに min/max レンジ付きで格納（1e6 固定小数点）。
- 同一 tech に**媒体別の記録を並存可**（紙で速攻成文化 → 後に石板へ写す「副本」動線）。「成文化済み」＝記録が1件以上存在すること。
- **焼失セマンティクス：** 燃えるのは記録であって知識ではない。可燃記録が全て失われても、生存保持者または不燃記録が残っていれば再成文化可能（当該 tech は未成文状態へ戻り、§11.2 の想起困難系が再適用される）。生存保持者ゼロかつ記録ゼロの場合のみ周回内喪失（(A) は次周再取得可・(B) は永久＝§10.2 と同一規則）。
- **MVP範囲：** 火災イベントは **MVP に1本も入れない**。engine には event 効果プリミティブ `destroyRecords{medium, scope}` のみ実装し conformance ベクタで挙動を固定する。火災は MVP 後に **additive な event JSON の追加だけ**で解禁できる（engine 変更なし・golden 不変・algoVersion bump 不要）。
- **アシスト整合：** おまかせ成文化ヒューリスティック（§2.1・残存tick降順80%）に規則を1つだけ追加 —「**唯一保持 tech は石板、それ以外は紙**」。80% 基準は不変。
- **sim整合：** §11.4-4「唯一保持者残存想定tick ≥ 成文化所要tick × 1.5」の所要 tick は**石板（遅い方）の値で評価**する（保守側）。
- **MVP対象外（将来オプションとして記録のみ）：** 書庫施設・熱源タグ隣接による火災リスク・大移動輸送中の記録喪失判定。

### 11.2 想起困難の発生式（中核ジレンマの数式化＝最重要）

`recallRisk(住民u, tech t)` を1ゲーム日（1440tick）ごとの発生確率として定義：

`p = clamp(0, base_p × loadW(施設負荷) + moraleW + dispatchW − masteryResist(u,t), p_max)`

| 変数 | 値 |
|---|---|
| base_p | 0.05 |
| p_max | 0.35 |
| loadW | 過酷業務（製錬/鍛冶/高炉等）就労で ×2.0、通常業務 ×0.5 |
| moraleW | 士気 <30 で +0.10、士気 <15 で +0.20 |
| dispatchW | 探索派遣中 +0.15 |
| masteryResist | 実地稼働で蓄積する定着度(0〜0.20) ＋記憶巧者trait −0.15 |

発生時：持続 `d = 1〜2日`（seed決定論）、その間当該住民の当該tech関連生産のみ停止（他生産・他住民は影響なし）。回復条件：通常業務就労かつ士気 ≥40 を持続、または療養所で休養1日。全パラメータを balance JSON に格納し min/max レンジ制約付与。決定論オフライン処理は逆CDFで次発生tickを一発サンプリングしジャンプ。

**[2026-07-27裁定] 日次確率 → step確率の按分は線形（裁定N1）。** 上式の `p` は 1ゲーム日（1440tick）あたりの確率である。粗粒度 step（`coarseTickMinutes`、MVP=10分）あたりの確率へは**線形按分**で落とす:

`p_step = p_day × coarse / 1440`

数学的に厳密な `1 - (1 - p_day)^(Δ/1440)` は**非整数べき乗であり ADR-006 の Math 許可リストで禁止**（固定小数点1e6・整数演算のみの原則を破る）。線形按分は `p_day` が小さい領域で厳密式の良い近似であり、その誤差の妥当性は先行計測 #5 で判定した（1.875回/住民/週＝§11.4-8 レンジ内）。11.8(C) の離散事象方式も同じ `p_step` を用いる。

**[2026-07-27裁定] mastery上限 0.20 の相殺挙動は MVP では現状維持（裁定N12）。** `masteryResist` の上限 0.20 は、過酷業務時の `base_p × loadW = 0.05 × 2.0 = 0.10` を完全に相殺し、`clamp` により発生確率が **0** になる（先行計測 #5 の `harsh-high-mastery` パターンで発生 0 件を実測）。つまり**熟練住民が増える後半ほど「想起困難」という日常危機フックが減衰する**構造になっている。不具合ではなくパラメータ設計の帰結であり、**MVP では現状維持**とし、13.1 の「バランス調整の段階的マイルストーン化」で再評価する。

**[2026-07-30裁定] mastery の蓄積式と停止範囲の解決（M13 正本化）。** ①定着度は「解禁済み tech の実地要件施設（`tech.fieldRequirement.facility`）で稼働している間」だけ蓄積し、レートは **`masteryGainPerFieldWorkDay = 0.00288/日`**（上限 0.20 到達まで約 69.4 実地稼働日。per-tick 値は 1 回だけの floor 除算で得るため、日次値は 1440 との整除性を保つ raw 値で与える）。暫定定数であり M39〜M41 で裁定 N12 と対にして再評価する。②「当該 tech 関連生産のみ停止」の解決も同じ `tech.fieldRequirement.facility` を用いる（停止範囲と定着蓄積が同一の場所から導かれ、engine が語彙を発明しない）。**実地要件が content に無い tech の発生時は当該住民の全生産停止へフォールバック**（黙って「何も止まらない」にしない安全側）。抑制の粒度は (住民, tech) 単位（`techMemoryByKey`）、判定ペア（全生存住民×全 research techId）と回復条件は縮約のまま維持し M14 の #5 本判定で再評価する。

### 11.7 固定小数点・決定論の必須要件

- 整数tick演算を最初から必須。浮動小数の非決定性根絶。
- 固定小数点スケール＝**全数値 1e6 固定**、除算は切り捨て（floor）方向に統一、複合式は「各乗算後に都度スケール補正＋floor丸め」の順序に固定。代表式ごとに期待値ユニットテストベクタを coding.md 相当に用意。
- 非整数べき乗（1.2^n, 1.15^Lv）は実行時計算を一切禁止し、オーサリング時に Lv別/n別 の固定小数点値を事前計算し JSON へ個別値として書き出す。
- 全集合演算（Σ隣接・Σ担当者）は安定文字列IDの辞書順にソートしてから計算、コレクションは Map 統一。
- **同一tick内優先順位固定：** 襲撃判定 → 負傷反映 → **想起困難の回復 → 想起困難の抽選** → 生産 → 研究 → 成文化完了 → 探索解決 → 死亡/全滅判定 → 衛星供給 → 幕塵メーター更新。（想起困難2段の追加は下記 [2026-07-27裁定] を参照）
- hash入力（累計tick/累計解禁/周回回数/継承点）は全て **BigInt** で扱う（MAX_SAFE_INTEGER 桁溢れ回避）、境界値simテスト追加。RNGはドメイン分離 `hash(worldSeed, domainTag, tick/dispatchId)`。

**[2026-07-27裁定] 同一tick優先順位への想起困難2段の正式追記（裁定B1）。** 旧文言には想起困難の項が無く、T5 実装（`src/engine/scheduler.ts` 周り）が「回復・抽選を負傷反映と生産の間に置く」解釈で実装していた。**この解釈をそのまま正本化する**。段番号は上記9段を 10 刻みで予約したうえで、想起困難の回復＝**段22**、抽選＝**段24**とする。

| 段 | 処理 |
|---|---|
| 10 | 襲撃判定 |
| 20 | 負傷反映 |
| **22** | **想起困難の回復** |
| **24** | **想起困難の抽選** |
| 30 | 生産 |
| 40 | 研究 |
| 50 | 成文化完了 |

この配置の帰結として、同一tickでは「回復した住民はその tick の生産に寄与し、抽選で発生した住民はその tick の生産から外れる」。tie-break の全順序は `(tick, パイプライン段, entityId)` で、同一キーの push は禁止（heap の内部配置が処理順に影響しない）。

### 11.8 オフライン差分の区間分類（fatal「閉形式が理論的に不成立」への回答）

区間を厳密に3種へ切り分ける：

- **(A) 定常生産区間**（レート一定・確率イベントなし）＝区分求積で閉形式計算。
- **(B) レート変化イベント**（研究完了/成文化完了/era昇格）＝イベント発生時刻で積分区間を分割し各区間別レートで閉形式 → 次イベントへジャンプするハイブリッド。同一tick複数発生は既定の優先順位パイプラインで順序解決。疑似コードを設計書に明記し先行プロトタイプ計測対象に含める。
- **(C) 確率イベント区間**（想起困難/襲撃/翳り率変動）＝閉形式解を持たないことを認め、毎tick逐次判定に戻すのでなく「次発生tickを幾何分布の逆CDFで決定論的に一発サンプリングし、その時刻へジャンプ」する離散事象方式に設計変更。**[2026-07-27裁定] (C) が用いる step 確率は `p_step = p_day × coarse / 1440` の線形按分とする（裁定N1）**——厳密式 `1 - (1 - p_day)^(Δ/1440)` は非整数べき乗で ADR-006 禁止のため。詳細と根拠は §11.2 の注記を参照。

各機構がどれに属するかを事前分類し、閉形式不能領域を(C)として正しく扱う。8GB機負荷軽減の前提が「全区間閉形式」という誤前提に依存しない設計へ修正。

### 11.9 クロック前進exploit対策

経過時間は 0〜72h に clamp ＋単調増加タイムスタンプを localStorage と IndexedDB の二重保存で巻き戻し検知。加えて実時間ウィンドウ（実10分）あたりに消化できる累積tickにレート制限を設け、「クロックを進めて再起動 → 保存 → また進める」の反復での実質無限消化を抑制。クライアント完結・バックエンドなしゆえ完全防止は原理的に不可能（残余リスク参照）。

### 12.2 event cond DSL（確定）

`branches[].cond` で参照可能な変数（`teamPower, difficulty, statWeights, hasTrait, maxStatHolder, injuryCount, equipType`）と許可演算子（`==, !=, <, <=, >, >=, &&, ||`）を JSON Schema でホワイトリスト化し、パーサ対応範囲を固定してから LLM 運営開始。未対応構文・未知変数参照はスキーマ検証で reject。

**[2026-07-31裁定] 変数の意味と効果係数の合成式（M22 実装の正本化。本節は変数名しか定めていなかった）**:

- `statWeights`（裸の識別子）= そのノードの statWeights の値の**総和**（DSL は MemberExpression 不許可のためオブジェクトはスカラ縮約のみ）。`maxStatHolder(stat)` = チーム内のその stat の**最大値**（1e6 固定小数点。ID を返しても content 側が比較を書けないため値を返す）。`injuryCount` = **自ノードを含む**判定失敗回数（負傷有無の文面分岐が自ノードの結果を語れる必要）。`equipType` = item/ロードアウト実装まで常に `"none"`（語彙のみ先行確定）。
- 効果係数: `successMod` は判定の左辺へ `successMod×R` を**加算**（roll が 0..R 一様のため「成功確率を p 上げる」と厳密同値。距離帯で R が違っても意味不変）。`difficultyMod`/`rewardMod` は `×(1+mod)`、`injuryRiskMul` は乗算。適用順は **choice → stance** に固定（floor 丸めの非可換性への決定論対策）。
- choice の自動選択（MVP は非対話）: 方針 `cautious` = successMod 最大 / `press` = rewardMod 最大（同値は添字小）。engine は選択肢ラベルを解釈しない。対話 UI（M32）は `selectChoiceIndex` の戻り値をプレイヤー回答で置換する差し替え点。
- 評価器の実装形: **パース = schema 側（jsep）・評価 = engine 側**（ロード時に型検査済み `CondExpr` へコンパイル、実行時の文字列パースゼロ・1e6 固定小数点の整数比較のみ）。

### 12.3 researchCost 目安レンジの基準点（動的n問題への回答）

新規テックの n はプレイヤー選択で変動するため、prereqグラフから「当該era内で取り得る n の最小値〜最大値」を機械算出し、その全域で researchCost 個別値が式 `base_era × 1.2^n` の ±X%（例 ±25%）以内に収まるかを検証するアルゴリズムをスキーマ検証段階で実行。単一点でなく到達可能 n の全域チェック。

### 12.4 週次LLM運営（JSONのみ・ロジック追加不可）

新テック葉（既存壁テック配下の横展開のみ、既存entityの prereqs/unlocks 改変禁止＝leaf限定を lint 機械強制）、新レシピ、新施設（既存タグ組合せ範囲）、新探索イベント/目的地、新特性、新衛星拠点タイプ、新冒険記テンプレ、季節/幕塵イベント。新メカニクスはコード変更でスコープ外。

**追加パイプライン：** スキーマ検証（型・必須・レンジ・leaf制約・逆参照・cond DSL・跨時代需要・nレンジ） → 段階的sim1000回 → 変更パス強制決定論ゲート → 統計クリープ検出（同カテゴリ同era効率分布のZ-score外れ値監視） → 人間merge → betaソーク → 本番昇格。

**組合せ相互作用のbisection：** 新規entityは1件ずつA/B（旧のみ vs 旧+新1件）でsim通過確認 → 通過分を束ねて最終ゲート。最終セットがfailした場合、新規集合を二分してsim再実行し失敗側を再帰分割する二分探索で原因entity（または最小相互作用ペア）を局所化。単独通過だが束ねてfailする相互作用起因を自動帰着。

### 12.5 セーブ互換

1. 状態をID参照保持。
2. additive-only、既存IDのリネーム/削除/意味変更禁止（削除はtombstone化）。**[2026-08-02裁定・台帳v15 追-2]** tombstone の具体表現＝ID をファイルに残したまま `tombstoned: true` を立てる soft-delete 方式（M51 実装）。復活（true→false）、および墓標化と同時の他フィールド変更（抱き合わせ）も reject。
3. tombstone逆参照チェック＝他entity（prereqs/inputs/unlocks）が参照し続ければreject、参照側同時修正を必須手順化。**[2026-08-02裁定・台帳v15 追-2]** 「参照側同時修正」は 12.4 の既存entity改変禁止と衝突し得るため（M51 が発見した構造的緊張）、**墓標化は末端（被参照ゼロ）の ID に限る**を運用規則とする。
4. **tombstone化を進行中セーブが参照するケースの救済：** マイグレーションに「tombstone化対象を研究キュー/装備中で参照する実行時セーブへの救済ルール＝着手済み進行は着手時点定義で完了継続を許可、未着手投入分は投入コスト返還」を追加。
5. 未知IDはロード時グレースフル無視、新規entityは未解禁で自然合流。
6. saveSchemaVersion＋contentVersion保存、起動時マイグレーション（純粋関数）。
7. worldSeed＋RNGカウンタ保存、確定済みtick結果はスナップショット固定・未来tickのみ新テーブル適用。探索イベント列は派遣時点スナップショット固定（再参照禁止）。帰還ログはレンダリング済み完成文字列保存（再参照禁止）。
8. **バランス調整のセーブ互換：** 既存パラメータ数値変更は許容、着手済みオーダーは着手時点パラメータをスナップショット確定・新規オーダーのみ新パラメータ。
9. ログ保持上限直近50件、超過は要約統計に畳む。セーブ全体サイズ定期検査し QuotaExceededError 前アラート。

### 12.6 PRNG/hashアルゴリズムの後方互換

PRNG/hash 関数を `algoVersion` として明示し worldSeed/セーブに埋め込む。コア実装のバグ修正・変更時は新 algoVersion 導入＋旧セーブは旧versionで未来tick計算を継続する互換レイヤーを設計。加えて「リリース後の algoVersion 1系は不可侵、変更は必ず新version追加」を運用ルール明文化。既存セーブの未来イベント（自動加入/襲撃/想起困難）が過去sim検証と食い違う事態を防ぐ。

## 14. 残余リスク（最終レビューで残った指摘を統合）

1. **(B)一回性喪失の情緒的手触り（唯一の未検証コア体験リスク）：** memoirLog/bond/記憶可視化をMVP実装しても最終的にはプレイテスト依存。決定論テンプレのエピソードが RimWorld 的な有機的物語の厚みに届くかは未検証で、届かなければ (B) 喪失が「名前付きレアドロップ損失」に留まる可能性が残る。喪失デモは一度きりの演出であり、本編での継続的な愛着形成を保証しない。

2. **配置パズルの固定化：** 過密ペナ＋周回シード揺らぎ（係数±20%・地形・資源稀少度）で緩和したが、タグ7種 × 施設14種 × 8近傍という組合せ空間は本質的に小さく、周回で別の単一準最適パターンに再収束する可能性は完全には消えない。static判定・完全情報公開ゆえ初回攻略でほぼ解けるという構造は残る。深さは隣接行列とペナ係数の質に依存しプレイテスト調整必須。

3. **アシスト80/100約束の体感成立性：** 実装で貪欲法の局所最適が理論最大に近づきすぎると +20% 上澄みが縮む。80/100の差が体感できる水準にパラメータ調整できるかは実測依存。ボタンを押さない自己規制でしか深さを体感できない構造的緊張も残る。

4. **8GB機の性能両立：** 単発オフライン復帰レイテンシ（2秒以内）と夜間バッチ（1000回 × 最大8bot）の両立は先行計測前は未確定。確率イベント区間(C)が想定より多ければ計算量が膨らみ、Fallback発動でも週次配信モデルの検証密度が下がるリスク。

5. **複数確率系の逆CDF合成：** オフライン差分は(C)確率区間を逆CDFジャンプで扱う設計に修正したが、複数確率系（想起困難・襲撃・翳り率）が同一区間で相互依存する場合の逆CDF合成は繊細で、実装バグで再現性が崩れれば sim検証・シード共有・オフライン復帰の全てが破綻する。最重点で工数配分するが残余。閉形式化できない領域が設計上存在しうる点は(C)として認めた上でジャンプ粒度に落としているが、相互依存合成の実装難度は先行プロト計測対象。

6. **バランス調整の収束保証：** era比×2統一とnのクリティカルパス限定で指数破綻とera間インフレは解消見込みだが、5戦略bot全てを各エラ到達レンジに収めるパラメータ調整と成文化コストのスイートスポット探索は狭く、段階的マイルストーン化しても2週で収束する保証は実測前にはない。researchCost個別値24件・adjacencyペナ係数・trait係数8種・outpost数式3タイプの同時多変数調整という実質的困難が残る。

7. **クロック前進exploit：** clamp＋二重タイムスタンプ＋レート制限で抑制するが、クライアント完結・バックエンドなしゆえ原理的に完全防止は不可能。シード共有の疑似競争の公平性は自己申告に依存する構造的弱点として残存。

8. **iOS Safari ITP / localStorage 7日削除：** エクスポート/インポート必須化＋バックアップリマインド＋PWAホーム追加導線＋persist API検証で対処するが、ユーザーがホーム追加もバックアップも実行しなければ全損リスクは残る。EU DMA下でのPWA standalone不可も含め2026実機挙動は先行フェーズで再確認が必要な未確定領域。

9. **PWA通知と自発習慣依存：** iOS（standalone必須）・EU DMA制約が強く、条件分岐で代替リテンションに逃がしても「1日1〜3回チェックイン」が自発習慣依存になり放置系として離脱率が悪化しうる。通知が機能しない環境での代替演出の効果自体も未検証。

10. **静的グラフ解析の網羅限界：** (A)再取得保証は、住民の生死・記憶状態・実地要件の動的条件をどこまで正しくモデル化できるかに依存。敵対bot6種で漏れを減らすが全状態空間網羅は原理的に不可能で、稀なエッジケースの本番顕在化は残る。

11. **ターゲット二層の同時満足：** 赤バッジ限定化・想起困難の黄バッジ化・難度シード「穏」でコア層の緊張感とライト層の放置安心感の衝突を緩和したが、日常危機化フックそのものがカジュアル層の「見なくても平気」期待と構造的に対立する点は残り、二層の同時満足はプレイテストで要検証。

12. **工数の暫定性：** 15〜17週へ再上方修正したが計測前の暫定逆算。コンテンツ単価が2〜3倍に振れれば、または1エンティティのsim通過イテレーションが想定超なら更に伸びる。1人＋AI開発でUI12画面・アシストアルゴリズム・バランス調整を並行できるかもスケジュール残余リスク。

13. **新規数式パラメータ初期値の妥当性：** trait上限3固定・住民寿命の対数正規近似・recallRisk の各係数など新規に数式化したパラメータの初期値は理論値であり、実際に「日常ジレンマとして毎日効く」頻度と「理不尽でない」の両立点に収まるかは sim反復とプレイテストでの調整に依存する。
