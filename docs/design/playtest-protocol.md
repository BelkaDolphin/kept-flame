# AIプレイテスト評価プロトコル(正本)

作成: 2026-08-02(統率者=Fable5)。ユーザー指示「ユーザビリティ等の評価を一定の基準・手順で繰り返し、品質を上げる」のタスク化。
初出の単発UX評価(2026-08-01・Opus 3体・fatal5/major8/minor9)を**定常運営の品質ゲート**へ昇格させるための手順書である。

## 1. 目的と位置づけ

- 実ブラウザ(Playwright)で「実際に遊べるか・遊びやすいか」を**同一の基準・同一の台本**で繰り返し評価し、ラウンド間でスコアを比較可能にする。
- テストプレイ加速モード(M59・×60/×720)を使い、**時間を要する実ゲーム挙動**(研究完了・探索帰還・想起困難・死亡/漂着・大移動)まで踏み込む。単発UX評価ではここが未踏だった。
- 本プロトコルは**評価のみ**を行う。修正は評価結果のトリアージ(§8)を経て別タスクとして投入する。
- 実施タイミング: UI/content に実質変更が入ったラウンドの節目(統率者判断)。最低でも M39(バランス調整)前・M43(最終検分)前に各1回。

## 2. 実施条件(固定)

| 項目 | 規定 |
|---|---|
| 対象ビルド | `npm run build` → `npm run preview -- --port <各自> --strictPort`(port は 4600 番台を使用。4237〜4336 は Windows 予約域のため禁止) |
| 初期状態 | ブラウザ文脈ごとに新規(storageState なし)。既存セーブが必要な台本は自分で到達して作る。IndexedDB 名は `kept-flame` |
| ビューポート | **390×844**(モバイル基準)/ **768×1024** / **1280×800** の3種。台本系は 390×844 を主、監査系は3種全部 |
| 加速モード | ヘッダの ⏩ で ×1/×60/×720。リロードで×1に戻る(仕様)。台本中の長時間区間のみ使用し、操作性計測区間は×1で行う |
| console | 全台本で console error / pageerror を収集。**error 1件でも fatal 候補**(内容で判定) |
| コード変更 | 評価エージェントはリポジトリのファイルを一切変更しない(Playwright スクリプトや結果 JSON は scratchpad に置く)。結果の repo 収容は統率者が行う |
| モデル | 評価エージェントは Opus/Sonnet(プロジェクト規約)。統率者は集計・裁定のみ |

## 3. 評価軸(5軸)

- **A. タスク達成**(§5 台本 T1〜T12): 初見プレイヤーが UI の情報だけで目的を達成できるか。
- **B. 進行健全性**: 加速して長時間進めたとき、ゲーム状態と画面表示が一貫し、進行不能・表示破綻・console error がないか。
- **C. UIヒューリスティック**: Nielsen 10 を本作向けに縮約した10項目(§6)を画面グループ別に採点。
- **D. フィードバック・文言**: 操作の結果が伝わるか。内部ID・開発メモの露出、reject 文言、成功フィードバック、用語一貫性。
- **E. レイアウト・基礎アクセシビリティ**: 機械検査系(§7)。

## 4. severity 定義(全軸共通)

| 級 | 定義 | 例 |
|---|---|---|
| **fatal** | 進行不能/データ破壊/虚偽表示(実装と異なる説明)/console error を伴う機能不全 | 派遣が完遂できない・大移動後ソフトロック(いずれも過去実例) |
| **major** | 主要タスクの達成を阻害するが回避策がある/初見が高確率で迷う | 資源が常設表示されない(過去実例) |
| **minor** | 磨き。達成には影響しない | 余白・文言の硬さ |

## 5. 軸A/B: タスク達成台本 T1〜T12(固定・変更は統率者裁定)

各タスクを 0〜2 で採点: **2**=UI の情報だけで迷いなく達成 / **1**=試行錯誤(誤タップ・画面往復・推測)の末に達成 / **0**=未達成(fatal 登録)。誤タップ数・所要ステップ数・引っかかった箇所を必ず記録する。

| ID | 台本 | 達成条件 |
|---|---|---|
| T1 | 新規開始→ホーム画面の理解 | 資源HUD・研究チップ・ナビ5グループを視認し「次に何をすべきか」を画面情報から言語化できる |
| T2 | 施設建設(かまど等)→就労割当 | 建設が資源を消費し、就労者を置くと産出が始まることが確認できる。**確認手段は在庫増加(×60以上の加速可)またはレート表示のどちらでも可**。微小レート(400スケールで 0.1/分 未満)が「0/分」等の虚偽表示にならず、束G②の表記(「<0.1/分」または小数桁可変)で読めること |
| T3 | 研究開始→×60加速→完了 | 研究チップの進捗が動き、完了が何らかの形で伝わる |
| T4 | 成文化キュー投入→完了→取消も1回試す | 媒体(石板/紙)を選べ、完了で(B)リスク表示が変わる。取消(返金なし)の文言確認 |
| T5 | 探索派遣(近郊)→×720→帰還 | 編成→派遣→帰還ダイジェスト表示まで。ROI・(B)損失表示の可読性も記録 |
| T6 | 開墾(瓦礫セル) | コスト表示→実行→建設可能になる |
| T7 | 増築 | コストと効果(Lv曲線)が事前に読める。**400スケールの微小レートでも Lv 間の差が判別できる表記であること**(小数丸めで前後 Lv が同値表示になったら fail) |
| T8 | 拠点設置→駐在→供給確認 | 供給が HUD/画面のどこで確認できるか記録 |
| T9 | 新施設(M58): 貯水槽→粘土・写字室→紙 | 粘土/紙が実際に入手でき、成文化(紙)へ繋がる。**寝床(寝床上限+N)・保管庫(保管上限加算)は実効果が正しく表示されるか、見張り台/療養所の2種のみ「効果は未実装」と正直に伝わるか**を記録 |
| T10 | export→import 往復 | 往復後にゲーム状態が保たれる |
| T11 | 長時間進行(×720でゲーム内7日以上) | 想起困難・死亡・晴天漂着のうち観測できたものと、その際の画面表示の整合(バッジ・トースト・ログ)。資源カーブの破綻(桁あふれ表示等)がないこと |
| T12 | 大移動→新周回→継承点購入 | ナップサック→実行→新周回が施設ありで開始→⑪で購入。周回後の資源・研究の初期表示が正しい |

軸Aスコア = T1〜T12 の平均(0〜2)。**軸B判定** = T11/T12 系で進行不能・表示破綻・console error が無いこと(あれば fatal)。

台本変更履歴(§5 の変更は統率者裁定を要する):
- [2026-08-03 台帳v16 必-3] T2/T7=400スケール(産出約1/3000)の表示解像度を前提に達成条件を書き直し(束G②の表記に整合)。T9=寝床/保管庫は実効果表示済みと判明(Round 2〜4 実測)のため「効果なし」検証対象を見張り台/療養所の2種に限定。

## 6. 軸C: UIヒューリスティック(10項目×画面グループ)

画面グループ: ①ホーム+HUD ②拠点(格子/施設詳細/住民) ③研究+成文化 ④探索+冒険記+拠点網 ⑤周回(大移動/継承)+設定。
各グループ×各項目を 0〜2(2=良い/1=支障はないが摩擦/0=阻害)で採点し、根拠を1行書く。

1. 状態の可視性(今何が起きているか常時わかる)
2. 現実との一致(用語がプレイヤー語彙か。内部用語の漏出なし)
3. 操作の自由(取消・戻る・やり直しが可能)
4. 一貫性(同じ操作は同じ見た目・同じ場所)
5. エラー予防(不可能な操作に入る前に分かる)
6. 再認優先(記憶を要求しない。必要情報がその場にある)
7. 効率(頻繁操作への近道。おまかせ系の発見性)
8. ミニマリズム(1画面の情報過密がない)
9. エラー回復(reject されたとき原因と対処が分かる)
10. ヘルプ(初見への導線。空状態メッセージの質)

軸Cスコア = 全セル平均(0〜2)。0 を付けたセルは finding として必ず起票する。

## 7. 軸D/E: 監査チェックリスト(機械検査系)

**軸D(文言・フィードバック)** — 各項目 pass/fail+件数:
- D1 内部ID・GDD番号・開発メモ・実装状況注記の露出 0件(13画面総なめ)
- D2 engine reject 発生時に日本語文言が出る(拒否コード生値の露出なし)
- D3 資源・施設・tech・イベントの表示名が和名(ID直訳露出なし)
- D4 破壊的/不可逆操作(大移動・リセット・取消)に事前警告がある
- D5 成功フィードバック(建設/増築/開墾/研究/成文化/派遣/拠点操作)が何らかの形で出る

**軸E(レイアウト・基礎a11y)** — 各項目 pass/fail+件数:
- E1 本文フォント 12px 未満 0件(3ビューポート)
- E2 タップターゲット 44px 未満の操作要素 0件(モバイル)
- E3 ページ横スクロール発生 0画面
- E4 格子タグの4重符号化(色+記号+パターン+数値)が全ズーム段で維持
- E5 sticky ヘッダ/ナビ/確定バーが3ビューポートで機能
- E6 console error / pageerror 0件(全監査経路)

## 8. 集計・成果物・合格基準

- 各エージェントは結果を**機械可読 JSON**(下記形)+所見リストで返す。統率者が `docs/measurements/playtest/round-NN-<date>.json` へ統合収容し、HTML レポート(Artifact)を発行する。

```json
{
  "round": 1, "date": "YYYY-MM-DD", "commit": "<hash>",
  "scores": { "A_task": 0.0, "C_heuristics": 0.0, "D_wording": "n/m pass", "E_layout": "n/m pass" },
  "B_health": { "fatal": 0, "notes": [] },
  "findings": [ { "id": "R1-F01", "severity": "fatal|major|minor", "axis": "A-E", "screen": "", "summary": "", "repro": "" } ]
}
```

- **合格基準(ラウンド共通)**: fatal 0 / 軸A平均 ≥ 1.5 / 軸C平均 ≥ 1.5 / 軸D・E の fail 項目 0 / **前ラウンドからのスコア悪化なし**(リグレッション検知)。
  - [2026-08-05 台帳v19 必-1] 深掘りにより**新経路の初回発見**が出た場合、「スコア悪化なし」の判定は**同一経路の再測定値**で行う。新経路での初回発見はリグレッションと区別する(評価解像度の向上による見かけの低下を不合格扱いしない)。前例: Round 6 軸C 1.94→1.83(成文化の取消→再投入→資金不足経路の初深掘りで新規minor 3件。挙動後退ゼロのため合格確定)。
- 不合格項目は fatal/major を「今やる」候補、minor を M39 等の既存再評価枠へトリアージし、裁定台帳またはレポートでユーザーへ提示する。
- 数値は**実測のみ**を記録する(推測値・未実施項目の捏造禁止。未実施は unmeasured と明記)。
- **部分ラウンド**([2026-08-02 台帳v14 追-3で追認]): 直前の修正が **UI 層のみ**(engine/balance/content 無変更)の場合に限り、検収対象の軸だけを完全実施し、残る軸は前ラウンド値の継承としてよい。継承・未実施は正本 JSON に必ず明記する。**engine/バランスへ触ったラウンドの後は全軸フル実施へ戻す**(Round 3 が前例: M62/M57 検収で軸C/D/E 完全実施・軸A/B は Round 2 値継承)。

## 9. 既知の限界(正直な開示)

- デスクトップ Chromium 中心の評価であり、実機(Android/iOS)の性能・タッチ感は②実機計測(M42)の領分。
- 加速モードはセッション限りで、加速下の可読性(トーストが流れる等)は等速時と異なる。加速起因の所見はその旨を明記する。
- 「楽しさ」「喪失の情緒的手触り」(GDD 残余リスク(B))は本プロトコルの射程外。人間プレイテスト依存のまま。

運用規定([2026-08-05 台帳v19 追-1] Round 6 の学びの明文化):

- **確率事象(想起困難・死亡・晴天漂着)の観測**: 観測待ちには上限時間(実時間5分目安)を切り、上限までに発生しなければ **unmeasured に降格して正直に記録**する(粘って捏造しない)。観測率を上げる台本改善として、①発生済みセーブ(export)の使い回し、②過酷業務への意図的配属による発生率の底上げ、を認める。
- **評価エージェントの停止禁止**: バックグラウンド通知や長時間待ちを理由に自主停止せず、**能動ポーリング(上限時間つき)で決着**させる。上限到達時は当該項目を unmeasured とし、残りの台本を完遂する。
