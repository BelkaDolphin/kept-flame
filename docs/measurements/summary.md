## 2. 合否判定の要旨(①完結 6 項目)

### 2.1 #3 / #4 — 正式合格(実 runner)

判断基準が「**GitHub Actions runner の wall-clock**」である以上、ローカル Ryzen の値では合否を出せない。T15 で `.github/workflows/calibrate.yml`(workflow_dispatch 限定・`contents: read`・LLM 要素ゼロ)を実 ubuntu-latest runner で走らせ、**実測環境そのもので基準を満たした**ため正式合格とする。

- ローカル参考値との比: #3 は runner/ローカル = 0.048705 / 0.035095 = **1.39 倍**、#4 は 0.408271 / 0.327726 = **1.25 倍**。runner のほうが遅いという事前予想(計画 §1)は実測で裏付けられた。
- 余裕度: 週次 11000 runs で目標 30 分に対し **8.93 分(29.8%)**。1 分 tick へ戻した最悪ケースでも **24.95 分(83.2%)** でなお枠内。ADR-014 の「2s/run 仮置き」に対して実測 0.0487s/run は **41 倍の余裕**。
- ただし本計測の bot は **2 本のみ**(計画 §2.2 の遵守)。MVP の 5 戦略 + 敵対 6 種 = 最大 11 本になった時点で `measuredSecPerRun` は再校正が必要(ADR-014(3))。現在の余裕(29.8%)は bot 数の増加を吸収できる幅として十分だが、**再校正の義務は消えない**。

### 2.2 #5 — 予備合格(縮約盤面である限定を明記)

**この判定は縮約盤面での予備判定であり、本判定ではない。** 計画 §1 および §8-8 が明記するとおり、想起困難頻度の本判定には住民系(memoirLog / bond / 寿命モデル)の実装が必要で、本フェーズの計測は recallRisk 式(GDD §11.2)のみを 10 分粒度で回した縮約モデルである。**住民系実装後に再計測すること**(GDD 13.1「住民系 1.5週」の完了時)。

そのうえで、実測データについて正直に記録すべき点が 2 つある。

**(a) 集計単位により判定が変わる。** 全体集計 **1.875 回/住民/週** は基準「週 1〜3 回」の中央付近にある。しかし 10 パターン別に見ると:

| パターン | 回/住民/週 | 基準 1〜3 に対して |
|---|---|---|
| 過酷業務/士気低/非派遣 | 2.875 | 範囲内(**最大**) |
| 過酷業務/士気低/派遣中(最悪ケース) | 2.8125 | 範囲内 |
| 通常業務/士気低/非派遣 | 2.6875 | 範囲内 |
| 過酷業務/士気高/派遣中 | 2.5 | 範囲内 |
| 過酷業務/士気中/非派遣 | 2.125 | 範囲内 |
| 通常業務/士気高/派遣中 | 2.125 | 範囲内 |
| 過酷業務/士気高/非派遣 | 1.625 | 範囲内 |
| 通常業務/士気中/非派遣 | 1.5625 | 範囲内 |
| **通常業務/士気高/非派遣** | **0.4375** | **下限割れ** |
| **過酷業務/士気高/定着度上限(0.20)/非派遣** | **0** | **下限割れ(発生ゼロ)** |

GDD §11.4-8 は「1住民あたり週1〜3回」としか書いておらず、**これを盤面平均で見るのかパターン単位で見るのかの定義が無い**。パターン単位で適用すると 10 中 2 が不合格になる。本書は「盤面平均で判定する」と解釈して予備合格としたが、**この解釈自体が要ユーザー判断**である(§6.1-B9)。

**(b) 定着度(mastery)上限 0.20 が過酷業務の base_p を完全に相殺し、発生確率が clamp で 0 になる。** これは計測で確認された挙動である(`harsh-high-mastery` パターンの発生 0 件)。含意として、**熟練住民が増える後半ほど「想起困難」という日常危機フックが機能しなくなる**方向の設計になっている。バランス上の発見であり不具合ではないが、GDD 3 章が「日常危機化」を中核フックに置いていることとの整合はユーザーに確認いただきたい(非ブロッキング・§6.3-N12)。

**[2026-07-30 M14・本判定へ更新]** 住民系(M11 寿命モデル・M12 memoir/bond・M13 tech別停止/mastery蓄積/実地要件フォールバック/(B)一回性喪失)の実装完了を受け、GDD 13.1「住民系 1.5週」完了時点の再計測義務(本節冒頭)を履行した。結果は **2.825 回/住民/週**(452発生/160住民週/8 seed)で引き続き盤面平均でレンジ内。判定単位=盤面平均(裁定B9)を GDD 11.4-8 へ明記済みのため、**本判定として合格**へ更新する(出典 `docs/measurements/recall-frequency-final-2026-07-30.json`)。1.875→2.825 の変化は mastery 蓄積式ではなく抑制粒度の変更(住民単位スカラ→(住民,tech)単位)が主因(同ファイル `verdict.changeFromPreliminary` に詳細)。パターン別下限割れは今回も2件(`normal-morale-high`=0.4375・`harsh-high-mastery`=0、いずれも上表と同一の力学)で、**引き続き不合格でなくバランス知見**として扱う。(a)(b) の指摘・§6.1-B9/§6.3-N12 の裁定内容自体は変更なし。

**判定ペア縮約(全生存住民×全research techId)の再評価(M14)**: 「保持者に絞る」場合の判定数・sim実行時間への影響を試算した結果、現時点では変更を推奨しない(性能上の緊急性なし・変更はengine挙動を変えるためalgoVersion bump相当・真のtriggerは施設14種content投入後の校正盤面更新)。試算の詳細は `docs/measurements/recall-frequency-final-2026-07-30.json` の `reductionPairReassessment` を参照。

### 2.4 #9a — 合格

`docs/design/tags-spec.md` に記載された 68 行(tag-ink × 面 6 種 + tag-ink × 自 tint + 中立色 × 面)すべてが WCAG 閾値を満たし、かつ **spec 記載値と計算値の乖離が全行 0.0045 以下**(許容差内)で一致した。spec に書かれた数値が机上の値ではなく実際に計算可能な値であることを機械で確認できた形になる。

余裕の薄い箇所は正直に記録しておく:

- テキスト用の最小値 **4.62**(lore ink vs rubble 面)— 閾値 4.5 に対し余裕 0.12
- 線用の最小値 **3.14**(lineGrid `#8A857D` vs rubble 面)— 閾値 3.0 に対し余裕 0.14

いずれも「これ以上明るくすると割る」下限に近い(tags-spec §9-6 が同じ指摘をしている)。今後パレットを触る場合は必ず `npm run measure:contrast` を再実行すること。

## 3. Fallback 発動提案

### 3.1 結論: **発動不要**(~~#12 のみ判断保留~~ **[2026-07-27 再測定により #12 も不要と確定 → 全項目で発動不要]**)

GDD §13.2 が定める Fallback は 2 系統ある。

**(A) 夜間バッチが枠を超える場合の 4 段**: ① 戦略 bot 5→3 に削減 → ② 毎晩→週次ゲートへ頻度低下 → ③ 1000回→層化サンプリング 200回 → ④ 粗粒度 tick 化(分 tick→10分 tick)

**(B) 単発レイテンシが 2 秒超の場合**: 代表シード + 粗粒度を設計に即組込む

| Fallback | 発動要否 | 根拠(実測) |
|---|---|---|
| ① bot 5→3 | **不要** | 週次 11000 runs が shards=1・**8.93 分**(目標 30 分の 29.8%)。bot 数増加ぶんの余裕がある |
| ② 毎晩→週次 | **不要** | 夜間 2200 runs = **1.79 分**。毎晩実行のコストが問題にならない |
| ③ 1000→層化 200 | **不要** | 同上 |
| ④ 分 tick→10分 tick | **不要(既に採用済み・かつ逆行の余地あり)** | MVP は最初から 10 分 tick。仮に 1 分 tick へ戻しても shards=3・**24.95 分**で枠内(#4)。つまり ④ は「発動する Fallback」ではなく「解除できる制約」の側にある |
| (B) 代表シード + 粗粒度の即組込み | **不要(暫定)** | デスクトップ 4 区間合計 **9.403ms** = 2000ms 予算の 0.47%。ただし **②実機で正式判定するまで「不要」を確定できない**(計画 §5.1) |
| #5 系の Fallback(該当系のみ1分tickへ戻す / 段階2前倒し) | **不要** | 1.875 回/住民/週 でレンジ内(§2.2 の限定つき) |
| #7 の Fallback(engine 当該演算を fp/整数へ矯正) | **不要** | 3 エンジン bit 一致。矯正対象の乖離箇所が存在しない |
| #9a の Fallback(色相/明度の再設計) | **不要** | 68 行全合格 |
| #12 の Fallback(MVP entity 数削減 / 週次投入単位の分割) | **不要 [2026-07-27再測定]** | 正味 wall-clock がレンジ下限 56h を約 3 桁下回る(§2.5 末尾)。entity 数削減・投入分割の理由が存在しない |

### 3.2 Fallback ではないが、実測から提案できる「削減」

計測結果が示す余裕は、Fallback(縮退)ではなく**実装の省略**として使える余地がある。いずれも **②実機計測の後**に確定すべき提案として挙げる。

1. **ADR-029 の「可変ドラフト in-place 更新」を MVP から外せる可能性。** T11 の B1 実測 7.4ms は**構造共有系(= 上限側)の値**であり、可変ドラフトは未実装(`catchUp.ts` で呼ぶと例外・`computeFidelity: "worker-structural-sharing"` として機械可読で宣言済み)。上限側の値ですら予算 1100ms の 0.67% であるため、実機の K が 100 倍でも 740ms で収まる計算になる。**ただし #2 のヒープ増分が unmeasured** であり、可変ドラフトの本来の目的は速度ではなくヒープ圧の削減(ADR-029)なので、**#2 を実機で測るまでこの提案は確定できない**。
2. **DOM 仮想化(ADR 692行の Fallback)は不要と見込める。** B4 mount 1.747ms(240 DOM)= 予算 200ms の 0.87%。

### 3.3 Fallback 発動権限について

計画 §8-11 が「不合格時に Fallback をこちらの判断で適用してよいか、都度承認か」をユーザー確認事項として挙げていたが、**本フェーズでは不合格項目がゼロだったため権限の行使機会が発生しなかった**。この問いは MVP 実装フェーズ(bot 11 本での再校正時など)へ持ち越す。
