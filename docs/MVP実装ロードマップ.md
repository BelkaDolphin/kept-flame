### 0.2 見積り方法

先行計測計画 §4.2 と**同じ方法**で「規模(新規ファイル数 / 概算実装行数)→ 素見積りトークン」を立て、summary §4.4-1 の運用提案に従い**一律 ×3.5** を掛けた値を計画値とする。セッション換算は `×3.5値 ÷ 2,000k`(summary §4.4 の 1 セッション ≒ 2M 実効)。

- 素見積りは先行フェーズの実績レンジに合わせる(Sonnet ≒ 30k + 0.15k/行、Opus ≒ 60k + 0.16k/行、Opus→Sonnet は両者の和)。
- 先行計測計画 §4.4 と同様、**±50% の幅**と**反復ぶんの上乗せ +30〜50%**が別途乗る(§5.1)。
- 週数(GDD 13.1)とトークン(本書)は**別軸**である。週数は人間開発者の作業週、トークンは LLM エージェントの消費量であり、両者の比率は一定でない(summary §4.1)。本書は週数を「どのマイルストーンの作業か」の対応付けにのみ使う。

### 0.3 実行モデル方針

ONBOARDING §6 の流儀を維持する。**Fable5(最上位)は統率・指示出し・検分のみで、実装コードを書かない。**

| 担当表記 | 割当基準(先行計測計画 §4.1 と同一) |
|---|---|
| **Opus** | 決定論の正当性が細部に宿るもの(値域証明・区間分類・tie-break・逆CDF・二系統更新)、algoVersion / セーブ互換に触れるもの、計測境界やアルゴリズムの設計 |

| Fable5 | 全タスクの検分(下表「検収条件」の**検分**部分)と、タスク間の裁定のみ |

### 4.2 律速列(クリティカルパス)

**M5 → M6 → M7 → M11 → M13 → M21 → M22 → M23 → M36 → M37 → M38 → M39 → M40 → M41 → M43**

合計 **8,210k ≒ 4.1 セッション相当**(全体 20,425k の **40%**)。

構造は「**engine 全系統化 → 住民系 → 探索/event → sim bot → バランス調整**」の一本道である。バランス調整(M39〜M41)は夜間ゲート(M38)が全 assert を持たないと着手できず、その M38 は 5戦略bot(M36)と敵対bot(M37)を要求し、その bot は想起リスク判断(M13)と探索(M21〜M23)を要求する。**したがって住民系と探索を後回しにすると最後のバランス工程がまるごと押し出される。**

**[2026-07-27裁定] 追加した運営基盤 5 件は律速列に乗らない。** M44 → M45 → M46 → M47 → M48 は合計 1,280k(0.64 セッション)で、律速列へは **M46 → M38 の 1 点だけで合流**する。M44〜M46 を Phase 0〜1 のうちに消化しておけば M38 を待たせない。M47/M48 は M34(PWA/ビルド)と M46 が揃えば走れるので、最長でも M5 → M8 → M29 → M34 → M47 → M48 = 3,000k で、律速列の 8,210k には遠く届かない。

### 4.3 並行投入できる束

**重要な前提: 並行投入はトークン総量を減らさない**(むしろ統率オーバーヘッドで微増する)。律速が週次利用上限である以上(summary §4.4)、並行の価値は「1セッションの 5 時間枠を使い切る」ことにあり、総セッション数の削減ではない。先行フェーズでは 3 並行(裁定 Opus + T8/T9 Sonnet = 888k)を実施し、`package.json` 共有は「Edit 限定 + 直前再読」で衝突ゼロだった(MEMORY 2026-07-26)。

| 束 | タスク | 律速列との関係 |
|---|---|---|
| **A**(セーブ列) | M3 → M4 | M5 以降と完全並行可 |
| **B**(格子列) | M16 → M17 → M18 → M19 | M11〜M14(住民列)と並行可 |
| **C**(UI列) | M8 → M29 → M30/M31/M32/M33 → M34 → M35 | M8 が M5 直後に開始でき、Phase 4 以降とほぼ全域で並行可。**最も長い非律速列**(2,915k ≒ 1.5 セッション) |
| **D**(conformance列) | M10 → M15 → M20 → M25 | 各 Phase の直後に薄く挿入。単独では走らせられない(先行タスクの成果を要求する) |
| **E**(文書列) | M1・M2 | 最初に単独で消化する。M2 は M3 以降すべての前提 |
| **F**(独立) | M9・M24・M26・M27・M28 | 前提さえ揃えば任意のタイミング |
| **G**(運営基盤列)**[2026-07-27裁定・追加]** | M44 → M45 → M46 → M47 → M48 | engine 列と全域で並行可(触るのは `.github/workflows/` `wrangler.toml` `CODEOWNERS` と運営スクリプトのみで、`src/` `schema/` `content/` に一切触れない = **最も衝突しにくい束**)。**M46 で M38 の前提として 1 点だけ合流する** |

**1 セッションあたりの詰め方の目安**: 平均タスクが 426k(20,425k ÷ 48)なので、**1 セッション(2M)= 3〜5 タスク**。異なる束から選んでファイル衝突を避ける。束 G は他のどの束ともファイルが重ならないため、**並行投入の埋め草として最も安全**である。

### 4.4 ②実機計測の合流点

②実機計測はユーザー実施・**期間不定**(summary §4.2 の新規行・§5.1)。合流点は 2 つに限られる。

| 合流点 | 何が変わるか | 実機を待たずに進める方法 |
|---|---|---|
| **M19 の既定ズーム倍率** | #9b の `minLegibleSizePx` が tags-spec §9-1 の既定ズームを決める(summary §4.2 の格子UI行が明記) | tags-spec の暫定値を**定数1箇所**に隔離して実装する。#9b 到着後は定数の差し替えのみで済み、UI 構造は手戻りしない(M19 の検収条件に入れた) |
| **M42(判定の確定)** | #1/#2/#8 の合否と、裁定 N13(可変ドラフト要否)の確定 | M42 以外の全タスク(M1〜M41)は実機結果を待たずに進行できる |

**実機不合格時に手戻りするタスク**は次の 4 つに限定される。それ以外は影響を受けない。

| 不合格項目 | 手戻り先 | 追加タスク |
|---|---|---|
| #2 ヒープ増分 > 48MB | catch-up 経路(`src/platform/catchUp.ts`)。二系統切替点が 1 箇所に隔離済みなので UI/engine への波及は無い | **M42a**(可変ドラフト実装) |
| #1 の B4 > 200ms | M18/M19(格子UIの DOM 構造) | **M42b**(DOM 仮想化) |
| #1 の B2 > 450ms | M3/M4(セーブ層)。512KB 想定(D1)での restore はデスクトップ 3.75ms | 既存タスク内で対処 |
| #1 の B3 > 250ms | M8/M29(ストアと派生値)。**そもそも M35 で取り直す前提**(summary §5.3-5) | 既存タスク内で対処 |

**実機を待たずに進められる範囲 = M42 / M43 以外の全タスク**(46/48 タスク・19,550k / 20,425k = **96%**)。実機が遅れてもロードマップは止まらない。運営基盤列(M44〜M48)も実機とは完全に独立である。

なお #10(ITP 7日)は実機入手後**最初に開始する**(待ち時間が最長・summary §5.2)。**[2026-07-28] iPhone 入手予定は当面なし → #10/#7-iOS は無期限保留**(入手時に即開始の原則は不変)。#6(段階2カスケード)は ADR-018(3) により MVP 対象外のまま。

### 5.2 セッション運用

- 予算単位は**トークンではなくセッション(5時間枠 ≒ 2M)**(summary §4.4-2)。
- 1 セッションに **3〜5 タスク**を、異なる束(§4.3)から選んで並行投入する。同一ファイルを触るタスクは同一セッションに入れない。`package.json` 等の共有ファイルは「Edit 限定 + 直前再読」を指示する(MEMORY 2026-07-26 の実績)。
- **Fable5 はセッションの冒頭(指示出し)と末尾(検分)のみに現れる。** 実装中の会話に入ると統率コストがトークンを食う。

### 5.3 MEMORY.md 記録規律(必須)

先行フェーズは 16 タスク中 7 タスクしか実消費を記録せず、**#11(週次セッション消費量)の代替データが不完全になった**(summary §4.4)。同じ失敗を繰り返さないため、**各タスク完了時に以下を MEMORY.md へ 1 行で記録することを完了条件に含める**(§0.4 の共通検収条件)。

[YYYY-MM-DD] MX完了(担当モデル・コミットハッシュ、Fable5検分: テスト件数): 見積りXXXk / 実消費YYYk / 比Z.ZZ倍 — 要点1〜3行

- **5 タスクごとに実績比を再計算し、§5.1 の係数 3.5 を実測値へ更新する**。更新したら本書 §5.1 を改訂する(本書は生きた文書として扱う)。
- セッション終了時には「そのセッションで消費した総トークン / 5時間枠の消費率」も記録する(1セッション ≒ 2M という前提そのものの検証データになる)。
