## 0. 目的と前提

### 0.1 このフェーズの目的

ADR末尾の計測12項目は、それぞれ**数値判断基準**を持つ。本フェーズの成果は「12項目に対する実測値と、基準に対する合否、不合格時のFallback発動判断」であり、その結果をもって GDD §13.1 の 15〜17週見積りを再計算する。ADR自体が「ms配分は計測で再調整前提の目標値」(ADR-012 トレードオフ)、「ヒープ/ポーズ数値は実機計測で再調整前提」(ADR-029 トレードオフ)、「2s/run は仮置きに過ぎない」(ADR-014)と明記しており、**計測前に本実装へ進むと設計前提が未検証のまま固定される**。

engine相当コードで `Math.random` / `Date.now` / `new Date()` / ADR-006許可リスト外の `Math.*` を使わない。LLM自動実行経路(headless/Actions連携/Agent SDK/Routines)を追加しない。content削除禁止(tombstone)。**ダークモード/ダークテーマ禁止**(計測用UI・ハーネスページ・スタイルガイド試作も light 固定とし、`prefers-color-scheme: dark` 分岐を書かない)。

## 1. 計測12項目の仕分け

判定は3区分。①=この Windows 環境(+GitHub Actions runner)で判断基準まで到達可能 / ②=デスクトップで予備計測し実機で本計測 / ③=実機・実運用でしか計測不可、先送り。

| # | 項目(ADR基準の要約) | 区分 | 根拠・条件 |
|---|---|---|---|
| 1 | オフライン復帰2秒予算: compute ≤1100ms / IDB+parse+deserialize ≤450ms / ハイドレーション ≤250ms / 約240 DOM ≤200ms | **②** | 4サブ予算の**内訳比率と絶対値の相対順位**はデスクトップで確定できるが、判断基準はターゲット実機基準の絶対 ms。実機必須 |
| 2 | GC/メモリ: ヒープ増分ピーク ≤48MB / GCポーズ ≤50ms/回 | **②** | Chromium系はデスクトップ/Android実機とも `performance.measureUserAgentSpecificMemory()` + DevTools Protocol で計測可。**iOS Safari はヒープ計測手段が事実上ない**ため iOS 側は近似(§6.3) |
| 3 | 夜間 sim の `measuredSecPerRun` 校正 → `shards=min(20, ceil(totalRuns×measuredSecPerRun/targetWallClock))`、週次11000 runs が360分キャップに余裕(目標<30分) | **①** | 実機不要。ただし判断基準は **GitHub Actions runner の wall-clock** ゆえ、ローカル Ryzen 実測は上振れする。**GitHub リポジトリ作成が前提**(§8-1) |
| 4 | Fallback(1分tick)発動時の再校正 | **①** | #3 と同一ハーネスで tick 粒度パラメータを変えるだけ |
| 5 | 粗粒度10分tickの体感両立: 想起困難頻度 週1〜3回/住民(GDD §11.4-8)かつ夜間batch枠内 | **①(縮約モデル)** | recallRisk 式(GDD §11.2)は完全に数式化済みで実装可能。ただし本計測は住民/施設/士気/派遣の実モデルに依存するため、先行フェーズでは**縮約盤面での予備判定**とし、本判定は住民系実装後に再計測(§8-8 要承認) |
| 6 | 段階2 next-reaction のカスケード被覆(敵対bot6種で全レジストリエントリ強制トリガー) | **③** | 段階2は MVP 後の追加投資(ADR-018(3)「段階2は MVP 後の追加投資ゆえ直近破綻ではない」)。段階2着手を決定した時点で実施。敵対bot6種の実装が前提 |
| 7 | クロスブラウザ golden vector 一致(Chromium/Firefox/WebKit で完全bit一致) | **①(3エンジン) / ②(実iOS Safari)** | Playwright 3エンジンは Windows で完結。**実 iOS Safari との一致は別問題**(§7) |
| 8 | Worker 越し state 転送(structured clone)コストが2秒予算内 | **②** | structured clone のコストは実機のメモリ帯域/GC に強く依存。デスクトップ値は下限見積りにしかならない |
| 9a | タグ7種記号・4重符号化の**コントラスト比** WCAG(非テキスト3:1 / テキスト4.5:1) | **①** | 色値から相対輝度比を計算するだけで機械判定可能。実機不要 |
| 9b | 44px角・最小表示スケール(ピンチ縮小)での**判読可否** | **②** | 物理DPI・サブピクセルレンダリング・実際のピンチ操作に依存。デスクトップのブラウザズームは近似にしかならない |
| 10 | ITP 7日免除の一次挙動(standalone/非standalone の IDB/localStorage 削除挙動) | **③** | iOS実機 + **7日以上の実時間経過**が必要。ADR-004(1)で設計はこの挙動に非依存化済み(バナーは最終起動 monotonicTimestamp のみでトリガー)ゆえ **MVPブロッカーではない**。実機入手後にバックグラウンドで開始 |
| 11 | 週次インタラクティブセッションのトークン/時間消費(Pro/Max週次上限に余裕) | **③** | content パイプライン(schema→sim1000→diff-gate→conformance→クリープ)一式が動く段階でしか実計測できない。**代替**: 本先行フェーズ自体の実消費トークンを記録し、上限余裕の一次見積りに使う(§4.4) |
| 12 | 1エンティティ制作素工数(56〜150hレンジのどこか。event は 1.5→2〜4h) | **①(縮約)** | 最小 schema + オーサリング手順を作り、tech/facility/event 各1本を**実測**すれば単価レンジを絞れる。全56〜150hを実施する必要はない |

### 仕分け結果の集計

- **① この環境で完結**: #3, #4, #5(縮約), #7(3エンジン), #9a, #12 → **6項目**
- **② デスクトップ予備 + 実機本計測**: #1, #2, #7(実iOS Safari補完), #8, #9b → **5項目**
- **③ 先送り(条件明記)**: #6(段階2着手時), #10(実機+7日経過), #11(contentパイプライン稼働後) → **3項目**

(#7 と #9 は性質の異なる下位項目に分割したため合計は12を超える)

**先送り3項目のMVPリスク評価**: #6 は段階2限定でMVPに掛からない。#10 は ADR-004 で設計非依存化済み。#11 は課金の壁(ADR-021)に関わるが、Phase 0 で「対話Claude Code=サブスク枠内」は公式確認済み(MEMORY.md)であり、残る不確実性は**消費量**のみ。よって**3項目の先送りは MVP 着手をブロックしない**と判断する。

- `git init` をローカルで実行。リモート(GitHub)は #3/#4 の Actions 実測に必須 → **§8-1 ユーザー確認事項**。
- **配置場所は要確認**(§8-7): 現状 `D:\develop\Claude\CaludeGame\` 直下に GDD/ADR/MEMORY 等が置かれている。ADR構成では設計文書は `docs/adr/` 配下。案は (a) 現ディレクトリをそのままリポジトリルート化し `src/` 等を追加して文書を `docs/` へ移動、(b) `D:\develop\Claude\kept-flame\` を新規に切り現文書を移設。**推奨は (a)**(移設による参照切れ・履歴断絶を避ける。`.claude/` と `lancedb/` は `.gitignore`)。

- `.editorconfig` で LF / UTF-8 (BOMなし) を固定。

### 3.3 Windows 固有の注意

- ファイル名の大小文字非区別: content ID は `^[a-z][a-zA-Z0-9_]*$`(ADR共通規約)で大文字を含みうるが**ファイル名は小文字統一**とし、Linux runner との差異を排除。golden vector ファイル名も小文字。
- パス長: Windows の 260 文字制限。`conformance/` 配下の seed 別ファイル名を長くしない(ハッシュ短縮形を使う)。
- `git config core.autocrlf` は `.gitattributes` が優先されるが、明示的に `false` を設定して二重防御。

### 4.1 モデル割当ての原則

`ONBOARDING.md` §6 のプロジェクト流儀に従う。**最上位モデルは統率・最終ジャッジのみ**、設計判断を含む実装は Opus、機械的・量産的作業は Sonnet。判断基準:

### 5.1 性能マージン係数 K の扱い(#1/#2/#8 共通の前提)

**[2026-07-27裁定] 校正カーネル方式は採用せず、実機直接計測で代替する(裁定D7)。** 以下の 1〜3 は**当初案であり、実施しない**。`bench/kernel.html` は実装しない。

- **代替方式(正)**: 実機で `dist/device/perf.html` を開き、**B1〜B4 の 4 区間を直接計測**して ADR-012(4) の各サブ予算と突合する。K を挟んだ外挿を行わないため、K の妥当性という追加の不確実性そのものが消える。
- **デスクトップ予備値の扱いは不変**: デスクトップ実測は引き続き `isOfficialVerdict: false` であり、**実機の直接計測が済むまで #1/#2/#8 を「合格」と宣言しない**(この原則は当初案から変更なし)。
- 実施手順の正本は `docs/measurements/device-testing-guide.md` であり、同 §8 の「`withProvisionalK` の値は無視する」という指示が正である(結果 JSON に暫定 K 由来のフィールドが残っていても判定に用いない)。

## 7. Playwright WebKit(Windows)の制約

ADR-017 の判断基準は「Chromium/Firefox/WebKit で3エンジン完全bit一致」であり、これは Playwright で Windows 上完結できる。ただし以下を明記する。

- Playwright の WebKit は **WebKit 本体をベースにした Playwright 独自ビルド**であり、Apple が iOS/macOS に出荷する Safari および WKWebView とはバージョン・ビルド構成・プラットフォーム層が一致しない。Windows 上のビルドは特に差が大きい。
- したがって #7 の 3エンジン一致で保証できるのは「V8 / SpiderMonkey / JavaScriptCore 系統をまたいで同一結果」までであり、**実 iOS Safari との一致は保証されない**。ADR-017 のトレードオフも「実 iOS Safari 完全一致は BrowserStack 相当で定期補完(open question)」と同じ扱いをしている。
- ただし決定論に効く主要因は既に構造的に潰されている: IEEE754 double 演算と整数演算は仕様上決定的、実装近似が許される `Math.pow`(非整数指数)/`exp`/`log`/`sin`/`cos`/`tan`/`atan2`/`cbrt`/`hypot` は**禁止**(ADR-006 精度表)、`localeCompare` 禁止(ADR-010)、キー順序依存は正準化パスで無効化(ADR-023)。**残る差分源は主に「禁止ルール違反の混入」であり、3エンジン一致テストはその検出器として十分機能する**。
- 実 iOS Safari 補完の手段は3案: (i) 実機 iPhone で `conformance/harness.html` を開き結果をコピーして突合(**追加コストゼロ・§6の実機計測に相乗り可能・推奨**)、(ii) BrowserStack 等の有料サービス、(iii) 補完しない(残余受容)。**(i) を推奨**し、実機入手までは (iii)。
